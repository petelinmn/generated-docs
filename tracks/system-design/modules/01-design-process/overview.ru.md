# Процесс проектирования и оценки

🌐 **Русский** · [English](overview.en.md)

## Коротко

System design начинается не со схемы из кубиков, а с вопросов и чисел: что система делает, какая на неё нагрузка, насколько она должна быть быстрой и доступной. Этот модуль даёт порядок действий и арифметику, на которой держатся остальные решения.

## Ключевые идеи

- Сначала требования: функциональные (что делает) и нефункциональные (как хорошо делает).
- Оценки «на салфетке» нужны для порядка величины, а не для точности.
- SLI измеряет, SLO задаёт цель, SLA — договор с последствиями.
- Обязательные зависимости понижают доступность, независимые реплики повышают.
- Задержку описывают перцентилями: среднее скрывает хвост.
- Чем шире fan-out, тем чаще пользователь видит хвост.
- Любое решение — компромисс, и его стоит записать.

## Минимальный пример

```csharp
double writesPerDay = 10_000_000 * 20;          // DAU * messages per user
double averageQps = writesPerDay / 86_400;      // about 2315
double peakQps = averageQps * 3;                // about 6944
```

## Когда применять, а когда нет

- ✅ Новая система или крупная фича, где ошибка в архитектуре дорога.
- ✅ Разговор о целях: «должно быть быстро» превращается в число.
- ✅ Собеседование по system design.
- ❌ Прототип на неделю: достаточно списка допущений.
- ❌ Точный прогноз мощности: нужны нагрузочные тесты и измерения.
