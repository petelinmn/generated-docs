# Хранение данных: базовая теория

🌐 **Русский** · [English](basics.en.md)

**Уровни:** [обзор](overview.ru.md) · **1. Базовая** · [2. Продвинутая](advanced.ru.md) · [3. Экспертная](expert.ru.md) · [4. Квиз](quiz.ru.md)

**Пререквизиты:** основы SQL · **Время:** ~2 ч

## Зачем это нужно

Сменить хранилище позже дорого: меняются запросы, транзакции и эксплуатация. Поэтому выбор начинают с вопросов: что читаем, по какому ключу, в каком порядке, как часто пишем.

## Модели хранилищ

| Модель | Сильная сторона | Типичное применение | Примеры |
|---|---|---|---|
| Реляционная | связи, транзакции, произвольные запросы | основные данные приложения | PostgreSQL, SQL Server |
| Ключ-значение | доступ по ключу | кэш, сессии | Redis |
| Документная | вложенный объект целиком | каталоги, профили | MongoDB |
| Wide-column | большой поток записи по ключу партиции | события, сообщения | Cassandra |
| Поисковый индекс | полнотекстовый поиск | поиск по каталогу и логам | [OpenSearch](../../../opensearch/modules/01-opensearch-basics/overview.ru.md) |
| Объектное хранилище | большие файлы | медиа, резервные копии | S3, Azure Blob Storage |

Если нет веской причины, начинают с реляционной базы. Несколько хранилищ в одной системе допустимы, но каждое нужно сопровождать и согласовывать.

## Паттерны доступа

Для чата: «последние 20 сообщений чата», «добавить сообщение», «найти по тексту». Первые два указывают на ключ `(chat_id, sent_at)`, третий — на отдельный поисковый индекс.

## Индексы

Индекс — это отдельная упорядоченная структура: по значению находит строку без просмотра всей таблицы. Каждая запись обновляет все индексы.

```csharp
// Every write pays for every index.
public void Upsert(Order order)
{
    if (_rows.TryGetValue(order.Id, out Order? old)) _byTotal.Remove((old.Total, old.Id));
    _rows[order.Id] = order;
    _byTotal.Add((order.Total, order.Id));
}
```

Файл: [Ex02_SecondaryIndex.cs](code/Examples/Ex02_SecondaryIndex.cs). Благодаря сортировке диапазон «сумма от 10 до 250» читается без перебора всех заказов.

## План запроса

SQLite отвечает на `EXPLAIN QUERY PLAN` строками: `SCAN` — просмотр всего, `SEARCH` — только нужной части. Для запроса последних сообщений без индекса план содержит `SCAN messages` и временное B-дерево для сортировки; с индексом `(chat_id, sent_at)` — `SEARCH messages USING INDEX ix_chat` без сортировки. Это показывают тесты в [Ex03_QueryPlans.cs](code/Examples/Ex03_QueryPlans.cs). Формат вывода может меняться между версиями: он для человека.

## Ошибки новичка

- ❌ Выбирать базу по популярности → ✅ по паттернам доступа.
- ❌ Хранить файлы в строках основной таблицы → ✅ объектное хранилище и ссылка.
- ❌ Не смотреть план → ✅ проверять на данных реального объёма.
- ❌ Считать, что индекс бесплатен → ✅ он занимает место и замедляет запись.
