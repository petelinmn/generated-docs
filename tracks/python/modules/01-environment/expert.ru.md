# Окружение и инструменты: экспертная теория

🌐 **Русский** · [English](expert.en.md)

**Уровни:** [обзор](overview.ru.md) · [1. Базовая](basics.ru.md) · [2. Продвинутая](advanced.ru.md) · **3. Экспертная** · [4. Квиз](quiz.ru.md)

Опирается на [продвинутую теорию](advanced.ru.md).

## Справочник запуска

| Команда | Назначение |
|---|---|
| `python script.py` | выполнить файл |
| `python -c "code"` | выполнить переданный фрагмент |
| `python -m package.module` | найти и выполнить модуль |
| `python -i script.py` | выполнить и оставить интерактивную оболочку |
| `python -I script.py` | изолированный режим CPython |
| `python -m venv .venv` | создать окружение |

Аргументы после `--` передаются программе и не интерпретируются Python как его флаги.

## Как устроен запуск

1. Выбран исполняемый интерпретатор.
2. CPython разбирает параметры и входную точку.
3. Скрипт или модуль компилируется в bytecode.
4. Импортирует модули и создаёт объекты по мере выполнения.
5. `sys.path` и переменные окружения влияют на поиск модулей.

Для файла `python script.py` первый элемент `sys.argv` содержит путь к скрипту. Для `python -m package.module` модуль запускается с флагом `__main__`, а имя исходного модуля доступно через `__name__`.

## Виртуальные окружения

Виртуальное окружение изолирует каталоги пакетов. Оно не копирует весь Python и не гарантирует воспроизводимость зависимостей само по себе: для этого нужен lock-файл или точные constraints.

В окружении создаются ссылки или исполняемые обёртки, настроенные на конкретный интерпретатор. Смена системного Python не должна заменять уже созданное окружение.

## Подвохи

### 1. `uv run` и активированный `venv`

Активирование окружения меняет `PATH`, но uv в проекте всё равно выбирает окружение проекта. Команды могут расходиться, если терминал открывал другой проект до активации.

### 2. Два Python и один pip

`pip` может принадлежать другому интерпретатору. Проверяйте так:

```python
import sys
print(sys.executable)
print(sys.prefix)
print(sys.base_prefix)
```

Если `sys.prefix == sys.base_prefix`, процесс работает вне виртуального окружения.

### 3. Текущий каталог не всегда имя пакета

Запуск `python package/cli.py` меняет первый элемент `sys.path` на каталог `package`, поэтому относительные импорты могут работать иначе, чем при `python -m package.cli`.

### 4. Байт-код не заменяет исходники

Проверка кэша по метаданным и timestamp не гарантирует неизменность исходного файла во всех окружениях. Для production-тестов проверяйте зависимости и исходник, а не только наличие `.pyc`.

## Вопросы с собеседований

<details><summary>1. Чем отличается скрипт от модуля?</summary>

Скрипт передается интерпретатору как файл; модуль находится механизмом импорта. `python -m` добавляет имя модуля и корректно обрабатывает пакеты.

</details>

<details><summary>2. Зачем нужен `uv.lock`?</summary>

Чтобы фиксировать точные выбранные версии и воспроизводить окружение независимо от изменения диапазонов в `pyproject.toml`.

</details>

<details><summary>3. Почему не стоит коммитить `.venv`?</summary>

Он содержит платформенно-зависимый локальный интерпретатор и кэшированные пакеты, а репозиторий должен хранить описания зависимости, а не копию среды.

</details>

<details><summary>4. Чем отличается `sys.prefix` от `sys.base_prefix`?</summary>

В обычном virtual environment `sys.prefix` указывает на окружение, а `sys.base_prefix` — на базовый интерпретатор.

</details>

<details><summary>5. Что делает `PYTHONPATH`?</summary>

Добавляет каталоги в начало или состав поиска модулей в зависимости от интерпретатора и параметров запуска. Это удобство разработки и отладочная настройка, а не замена пакетов.

</details>

<details><summary>6. Как проверить, что пакет принадлежит активному окружению?</summary>

Сравнить `sys.executable`, `sys.prefix` и расположение пакета из `importlib.util.find_spec()`.

</details>

<details><summary>7. Чем изолированный режим `-I` отличается от обычного запуска?</summary>

Он игнорирует `PYTHON*` и не добавляет текущий каталог или пользовательские пакеты к путям поиска, поэтому запускаемый скрипт менее чувствителен к локальному окружению.

</details>

<details><summary>8. Почему нельзя считать virtual environment переносимым артефактом?</summary>

Обычно его конфигурация привязана к абсолютным путям и ОС. Переносить нужно манифест и lock-файл, затем создать окружение заново.

</details>

<details><summary>9. Что произойдет при запуске скрипта до установки зависимостей?</summary>

Импорт нужного пакета завершится `ModuleNotFoundError`, даже если пакет установлен в другой venv.

</details>

<details><summary>10. Чем bytecode `.pyc` отличается от исходного `.py`?</summary>

`.pyc` содержит скомпилированный для CPython bytecode и является производным артефактом. Исходник остаётся основой и может быть прочитан другими инструментами.

</details>

## Компромиссы и альтернативы

- uv удобнее для быстрого проекта, системный пакетный менеджер нужен для системных библиотек.
- `venv` входит в стандартную библиотеку; uv быстрее и объединяет несколько операций.
- Conda полезен для сложных нативных зависимостей, но не заменяет описание пакета pyproject.
