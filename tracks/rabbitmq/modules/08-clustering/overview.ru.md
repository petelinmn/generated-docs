# Кластеризация и высокая доступность

🌐 **Русский** · [English](overview.en.md)

## Коротко

Кластер — несколько узлов RabbitMQ с общими метаданными: клиент подключается к любому, а операции над очередью пересылаются на узел, где она живёт. Высокую доступность дают **quorum-очереди**: они реплицируются и работают, пока доступно большинство реплик. Classic-очередь живёт на одном узле и недоступна при его отказе.

## Ключевые идеи

- **Метаданные общие, данные очередей — нет.**
- **Узел присоединяют так:** `stop_app`, `join_cluster rabbit@первый`, `start_app`.
- **Отказ узла:** classic-очередь недоступна (`404 … process is stopped by supervisor`), quorum продолжает работать.
- **Большинство:** 3 узла переживают 1 отказ, 5 — 2; двух узлов и чётных чисел избегайте.
- **Без большинства запись не подтверждается** (`timeout`), а не отвергается.
- **Перед обслуживанием:** `check_if_node_is_quorum_critical`, `rabbitmq-upgrade drain`, затем `revive`.
- **Стенд — учебный** (три контейнера на одной машине): сетевые разделения здесь не воспроизводились.

## Минимальный пример

```bash
docker exec rmq2 rabbitmqctl stop_app
docker exec rmq2 rabbitmqctl join_cluster rabbit@rmq1
docker exec rmq2 rabbitmqctl start_app
```

Всё запускалось на трёх контейнерах RabbitMQ 4.4.1 (см. [базовую теорию](basics.ru.md)).

## Когда применять и когда нет

| Нужно | Решение |
|---|---|
| Пережить отказ узла без потери сообщений | кластер из 3 узлов + quorum + persistent |
| Простая одиночная установка | один узел, осознавая риск |
| Связать независимые брокеры | Federation/Shovel ([дорожная карта](../../overview.ru.md)) |

- ❌ Не делайте кластер из двух узлов «для надёжности».
- ❌ Не считайте classic-очередь высокодоступной.
