# Управление потоком и производительность

🌐 **Русский** · [English](overview.en.md)

## Коротко

Скорость RabbitMQ определяется подтверждениями издателя, `prefetch` и подтверждениями потребителя, размером сообщений, типом очереди и настройками диска/памяти. Брокер защищается от перегрузки управлением потоком (credit flow) и оповещениями по памяти и диску, блокирующими издателей. Цифры в материале — **соотношения** на одной машине, а не прогноз для вашей системы.

## Ключевые идеи

- **Подтверждения конвейером** вместо «по одному»; без confirms вы меряете клиента, а не брокера.
- **`prefetch_count=1` — в десятки раз медленнее** (1,8 против 29,4 тыс. сообщений/с); для долгих задач это плата за справедливость.
- **Групповой ack** ускоряет чтение вдвое (66,8 тыс.), но требует идемпотентности.
- **Размер:** крупнее сообщения — меньше сообщений/с и больше МБ/с.
- **Quorum медленнее classic** (23 тыс. против 32 тыс.) — цена репликации.
- **Тревоги** по памяти/диску блокируют издателей: `Connection.Blocked` (`low on memory`/`low on disk`).
- **Лимит диска** срабатывает, когда свободно меньше лимита.

## Минимальный пример

```python
y.basic_qos(prefetch_count=1000)
y.basic_consume("perf", cb)   # cb acks every 100th message with multiple=True
```

Всё запускалось на настоящем RabbitMQ 4.4.1 в Docker (см. [базовую теорию](basics.ru.md)).

## Когда применять и когда нет

| Задача | Настройка |
|---|---|
| Много быстрых коротких задач | prefetch в сотни, групповые ack |
| Долгие неравные задачи | prefetch 1–несколько |
| Важные данные | confirms + quorum, с оценкой цены |
| Огромные данные | хранилище + ссылка в сообщении |

- ❌ Не принимайте решений по чужим бенчмаркам.
- ❌ Не настраивайте вслепую: сначала измерьте.
