# Шаблоны обмена сообщениями: экспертный уровень

🌐 **Русский** · [English](expert.en.md)

**Уровни:** [overview](overview.ru.md) · [1. Основы](basics.ru.md) · [2. Продвинутый](advanced.ru.md) · **3. Эксперт** · [4. Квиз](quiz.ru.md)

Опирается на [базовую](basics.ru.md) и [продвинутую](advanced.ru.md) теорию. «Проверено» означает наблюдалось на RabbitMQ 4.4.1 с pika 1.5.0.

## Справочник

### Шаблон → конструкции AMQP

| Шаблон | Обменник | Очередь | Ключевые свойства сообщения | Проверено |
|---|---|---|---|---|
| Work queue | default (`""`), ключ = имя очереди | durable, общая | `delivery_mode=2` | да |
| Pub/sub | `fanout` | `exclusive`, имя от сервера (`amq.gen-…`) | — | да |
| Routing | `direct` | по привязке на ключ | routing key | да |
| Topics | `topic` | по шаблонам привязки | routing key с точками | [модуль 02](../02-exchanges-and-routing/expert.ru.md) |
| RPC | default | очередь запросов + reply | `reply_to`, `correlation_id`, `expiration` | да |

### Свойства сообщения, важные для шаблонов

| Свойство | Для чего | Кто устанавливает |
|---|---|---|
| `reply_to` | адрес ответа | клиент RPC |
| `correlation_id` | связать ответ с запросом | клиент ставит, сервер копирует |
| `message_id` | идентификатор для дедупликации | издатель |
| `expiration` | TTL запроса в мс (строка) | клиент RPC |
| `delivery_mode` | 2 = persistent | издатель |
| `headers` | произвольные поля | издатель |

Брокер **не интерпретирует** `reply_to` и `correlation_id` (кроме псевдоочереди `amq.rabbitmq.reply-to`): это соглашение клиента и сервера.

### Direct reply-to

| Требование | Результат нарушения (проверено) |
|---|---|
| подписка с `auto_ack=True` | `406 PRECONDITION_FAILED - reply consumer cannot acknowledge` |
| подписка до публикации с таким `reply_to` | канал закрылся |

## Внутреннее устройство

- **Распределение в work queue — по готовности.** Брокер выбирает следующего потребителя, у которого есть «место» (prefetch). Поэтому быстрый воркер получил 9 задач из 10 (проверено); равного деления нет.
- **Fanout копирует по ссылке на уровне брокера**, но для вас это независимые сообщения в независимых очередях: подтверждение в одной очереди не влияет на другую.
- **Pub/sub без очереди — ничего.** Обменник не хранит сообщения; публикация без привязок молча теряется (проверено, если нет mandatory).
- **RPC не имеет состояния на брокере.** Брокер видит два независимых сообщения; связь — на стороне клиента (словарь ожидающих запросов).

> ⚠️ Проверить: внутренние детали direct reply-to (псевдоадрес, привязка к каналу) взяты из документации и здесь не проверялись.

## Подвохи

### 1. Fanout и общая очередь

Если два подписчика читают **одну** именованную очередь, сообщения делятся, а не копируются: это work queue, а не pub/sub.

### 2. Зависший RPC

Без таймаута и `expiration` запрос живёт, пока не появится сервер. Проверено: после таймаута клиента запрос с `expiration` исчез из очереди (`stale request still queued: 0`).

### 3. Поздний ответ

Ответ может прийти после таймаута. Клиент, удаливший `correlation_id` из ожидающих, должен просто игнорировать его (проверено: `pending after late reply: 0`).

### 4. Чужой `correlation_id`

Клиент, который складывает **все** ответы в словарь без проверки, получит и «чужие» (проверено: ответ с id `other` попал в словарь). Принимайте только ожидаемые id.

### 5. Reply-to без подписки

Публикация с `reply_to="amq.rabbitmq.reply-to"` без подписки закрывает канал (проверено).

### 6. Медленный воркер без prefetch

Распределение по кругу без prefetch не учитывает длительность задач: медленный воркер копит очередь. Проверяется в [модуле 03](../03-queues-and-delivery/expert.ru.md).

## Компромиссы и альтернативы

| Выбор | Плюсы | Минусы |
|---|---|---|
| Work queue | простота, горизонтальное масштабирование | нет порядка между воркерами |
| Pub/sub | развязка издателя и подписчиков | временные очереди теряют сообщения при отключении |
| RPC через брокер | готовый транспорт, балансировка | связывает по времени, нужны таймауты и дедупликация |
| HTTP/gRPC | синхронный контракт, проще отладка | нет буфера при недоступности сервера |
| Команда + событие-результат | устойчиво и асинхронно | сложнее клиент |

## Вопросы с собеседований

<details><summary>1. Чем work queue отличается от pub/sub?</summary>

В work queue каждое сообщение достаётся одному воркеру из общей очереди; в pub/sub у каждого подписчика своя очередь, и каждый получает копию.

→ [Базовая теория](basics.ru.md#work-queue)

</details>

<details><summary>2. Как временная очередь получает имя и когда исчезает?</summary>

`queue_declare("", exclusive=True)`: имя выдаёт брокер (`amq.gen-…`); очередь удаляется вместе с соединением.

→ [Базовая теория](basics.ru.md#publishsubscribe)

</details>

<details><summary>3. Подвох: два потребителя читают одну именованную очередь, привязанную к fanout. Оба получат все сообщения?</summary>

Нет: очередь одна, сообщения делятся между потребителями.

→ [Подвох 1](#1-fanout-и-общая-очередь)

</details>

<details><summary>4. Зачем `correlation_id` в RPC?</summary>

Одна очередь ответов обслуживает много запросов; по id клиент сопоставляет ответ с запросом.

→ [Базовая теория](basics.ru.md#rpc)

</details>

<details><summary>5. Что даёт direct reply-to?</summary>

Не нужно создавать очередь ответов на клиента: ответ доставляется на канал через псевдоочередь `amq.rabbitmq.reply-to`.

→ [Продвинутая теория](advanced.ru.md#direct-reply-to)

</details>

<details><summary>6. Подвох: можно ли подписаться на `amq.rabbitmq.reply-to` с ручным подтверждением?</summary>

Нет: `406 PRECONDITION_FAILED - reply consumer cannot acknowledge`.

→ [Справочник](#direct-reply-to)

</details>

<details><summary>7. Зачем ставить `expiration` на запрос RPC?</summary>

Чтобы запрос от ушедшего клиента не дожидался сервера и не выполнялся зря.

→ [Продвинутая теория](advanced.ru.md#rpc-клиент-с-таймаутом)

</details>

<details><summary>8. Что делает клиент с ответом, пришедшим после таймаута?</summary>

Игнорирует: id уже удалён из ожидающих.

→ [Подвох 3](#3-поздний-ответ)

</details>

<details><summary>9. Подвох: что произойдёт, если опубликовать в fanout до появления подписчиков?</summary>

Сообщение пропадёт: обменник ничего не хранит.

→ [Базовая теория](basics.ru.md#publishsubscribe)

</details>

<details><summary>10. Когда RPC через брокер — плохая идея?</summary>

Когда ответ не нужен немедленно: RPC связывает доступность клиента с сервером; лучше команда плюс событие-результат.

→ [Продвинутая теория](advanced.ru.md#выбор-шаблона)

</details>

<details><summary>11. Как быстрый воркер получил 9 задач из 10?</summary>

Брокер выдаёт сообщение тому, у кого есть «место» (prefetch); быстрый освобождается чаще.

→ [Базовая теория](basics.ru.md#work-queue)

</details>

<details><summary>12. Подвох: брокер сам связывает ответ с запросом по `correlation_id`?</summary>

Нет: это соглашение клиента и сервера; брокер не интерпретирует свойство.

→ [Справочник](#свойства-сообщения-важные-для-шаблонов)

</details>

## Шпаргалка

```text
work queue : durable queue, basic_qos(1), ack after work, delivery_mode=2
pub/sub    : fanout exchange + queue_declare("", exclusive=True) per subscriber
routing    : direct exchange, one binding per key
rpc        : reply_to + correlation_id (+ expiration); amq.rabbitmq.reply-to needs auto_ack=True
```

- Одна очередь — делим; очередь на подписчика — копируем.
- В RPC всегда таймаут.
- Подписка на reply-to — до публикации.
