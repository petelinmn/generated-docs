# Безопасность

🌐 **Русский** · [English](overview.en.md)

## Коротко

Доступ к RabbitMQ строится из **vhost-ов** (изоляция), **пользователей** и **прав** — трёх регулярных выражений (`configure`, `write`, `read`) на пару «пользователь — vhost». Теги определяют доступ к управлению. Сетевой трафик защищает **TLS**: брокер слушает отдельный порт (5671), клиент проверяет сертификат и имя хоста.

## Ключевые идеи

- **Права — регулярные выражения по имени ресурса;** `^$` не разрешает ничего.
- **Отказ при подключении:** неверный пароль и неизвестный пользователь — одинаковый `403 ACCESS_REFUSED`; нет прав на vhost — `530 NOT_ALLOWED`.
- **Нарушение прав на ресурс закрывает канал** (`403`), а не соединение.
- **Публикация в очередь через `""` требует `write` на `amq.default`.**
- **Отказ в публикации не бросает исключение:** виден по закрытию канала.
- **Теги:** `monitoring` читает API управления, без тегов — 401.
- **`guest`/`guest` удалите;** в учебном образе он доступен снаружи.
- **TLS с проверкой:** неизвестный CA и неверное имя хоста отклоняются.

## Минимальный пример

```text
rabbitmqctl add_vhost shop
rabbitmqctl add_user alice pw1
rabbitmqctl set_permissions -p shop alice "^app\..*" "^app\..*" "^app\..*"
```

Всё запускалось на настоящем RabbitMQ 4.4.1 в Docker (см. [базовую теорию](basics.ru.md)).

## Когда применять и когда нет

| Нужно | Решение |
|---|---|
| Изолировать приложения | vhost на приложение |
| Ограничить действия сервиса | минимальные регулярные выражения |
| Защитить трафик | TLS с проверкой сертификата |
| Доступ мониторингу без данных | тег `monitoring` |

- ❌ Не оставляйте `guest` и не раздавайте `.*`.
- ❌ Не отключайте проверку сертификата.
