# Безопасность: экспертный уровень

🌐 **Русский** · [English](expert.en.md)

**Уровни:** [overview](overview.ru.md) · [1. Основы](basics.ru.md) · [2. Продвинутый](advanced.ru.md) · **3. Эксперт** · [4. Квиз](quiz.ru.md)

Опирается на [базовую](basics.ru.md) и [продвинутую](advanced.ru.md) теорию. «Проверено» означает наблюдалось на одном узле RabbitMQ 4.4.1 (Docker).

## Справочник

### Команды управления доступом

| Команда | Назначение | Проверено |
|---|---|---|
| `rabbitmqctl add_vhost` / `delete_vhost` | создать/удалить vhost | да |
| `rabbitmqctl add_user` / `delete_user` | пользователи | да |
| `rabbitmqctl change_password` | сменить пароль | да |
| `rabbitmqctl set_permissions -p <vhost> <user> <configure> <write> <read>` | права | да |
| `rabbitmqctl list_permissions -p <vhost>` / `list_users` | просмотр | да |
| `rabbitmqctl set_user_tags` | теги пользователя | да |
| `rabbitmqctl set_topic_permissions`, `clear_permissions`, `authenticate_user` | права на топики и очистка | не проверялись |

### Результаты отказов (проверено)

| Ситуация | Код | Что закрывается |
|---|---|---|
| неверный пароль / неизвестный пользователь | `403 ACCESS_REFUSED` | соединение |
| нет прав на vhost | `530 NOT_ALLOWED` | соединение |
| нет `configure` на ресурс | `403 ACCESS_REFUSED` | канал |
| нет `write` на обменник | канал закрыт | канал |
| обычный AMQP на TLS-порт | `IncompatibleProtocolError` | соединение |

### Теги и доступ к управлению

| Тег пользователя | Доступ к `/api/overview` (проверено) |
|---|---|
| `monitoring` | 200 |
| нет тегов | 401 |
| `administrator` (`guest`) | 200 |

### Значения по умолчанию, считанные с брокера

| Параметр | Значение |
|---|---|
| `loopback_users` | `[]` в образе (по умолчанию в самом брокере `guest` ограничен `localhost`) |
| `max_message_size` | 16777216 (16 МиБ) |

> ⚠️ Проверить: ограничение `guest` по умолчанию и действие `max_message_size` (отказ при публикации больших сообщений) здесь не проверялись.

## Внутреннее устройство

- **Права проверяются по имени ресурса** регулярным выражением; пустое выражение `^$` ничего не разрешает.
- **Обменник по умолчанию называется `amq.default`:** публикация в очередь через него требует `write` на это имя (проверено).
- **Отказ в публикации не возвращается вызову:** канал закрывается асинхронно (проверено).
- **Одинаковый ответ на неверный пароль и неизвестного пользователя** не раскрывает, какие учётные записи существуют.
- **TLS-слушатель — отдельный порт** (5671), AMQP-порт остаётся, если его не отключить (проверено списком слушателей).

> ⚠️ Проверить: внутренние механизмы аутентификации (внешние источники: LDAP, OAuth 2), права на топики, влияние регулярных выражений на производительность и поведение при отзыве прав у уже подключённого пользователя здесь не проверялись.

## Подвохи

### 1. Слишком широкие права

Права `.* .* .*` отдают пользователю весь vhost. Давайте минимум.

### 2. Публикация в очередь требует права на `amq.default`

Без него канал закрывается молча (проверено).

### 3. Отказ в публикации не бросает исключение

Асинхронная публикация: видно только закрытие канала.

### 4. `guest` в образе открыт снаружи

`loopback_users` пуст в учебном образе: такой пользователь в рабочей системе — дыра.

### 5. Python отвергает CA без `keyUsage`

Строгая проверка сертификатов в Python: `CA cert does not include key usage extension` (проверено).

### 6. TLS без проверки — не защита

Отключив проверку сертификата, вы получите шифрование без уверенности, с кем говорите.

### 7. Пустые права ничего не разрешают

Пустое выражение `^$` не совпадает ни с одним именем, поэтому ничего не разрешает (проверено на `configure` и `write` у `bob`). Нужно ли для подключения к vhost хотя бы одно непустое право, здесь не проверялось.

## Компромиссы и альтернативы

| Выбор | Плюсы | Минусы |
|---|---|---|
| Один vhost на приложение | изоляция и простые права | больше vhost-ов |
| Общий vhost | проще | права сложнее, риск конфликтов имён |
| Пароли в брокере | просто | нужна ротация |
| Внешний источник (LDAP/OAuth) | единая учётная система | отдельная настройка; здесь не проверялась |
| TLS на брокере | шифрование, проверка сервера | управление сертификатами |
| TLS на прокси/балансировщике | удобно | нешифрованный участок внутри |

## Вопросы с собеседований

<details><summary>1. Из чего состоят права доступа в RabbitMQ?</summary>

Из трёх регулярных выражений (`configure`, `write`, `read`) на пару «пользователь — vhost»; сопоставляются с именем ресурса.

→ [Основы](basics.ru.md#три-уровня-доступа)

</details>

<details><summary>2. Подвох: брокер отвечает на неверный пароль и неизвестного пользователя по-разному?</summary>

Нет: одинаково (`403 ACCESS_REFUSED`), чтобы не раскрывать существование пользователя.

→ [Основы](basics.ru.md#что-происходит-при-отказе)

</details>

<details><summary>3. Что произойдёт при нарушении прав на `configure`?</summary>

Канал закроется с `403 ACCESS_REFUSED`; соединение остаётся.

→ [Основы](basics.ru.md#права-на-операции)

</details>

<details><summary>4. Подвох: пользователь с правом `write` на `^app\..*` публикует в очередь через `""`. Получится?</summary>

Нет: нужен `write` на `amq.default`; канал закроется.

→ [Подвох 2](#2-публикация-в-очередь-требует-права-на-amqdefault)

</details>

<details><summary>5. Как узнать об отказе в публикации?</summary>

По закрытию канала (асинхронно); исключения в вызове не будет.

→ [Подвох 3](#3-отказ-в-публикации-не-бросает-исключение)

</details>

<details><summary>6. Зачем vhost?</summary>

Изолированное пространство имён с отдельными ресурсами и правами.

→ [Основы](basics.ru.md#три-уровня-доступа)

</details>

<details><summary>7. Что делают теги пользователя?</summary>

Определяют доступ к плагину управления: `monitoring` — чтение API, без тегов — отказ (401).

→ [Основы](basics.ru.md#теги-и-управление)

</details>

<details><summary>8. Подвох: пользователь `guest` безопасен?</summary>

Нет: удалите его или смените пароль; в учебном образе он доступен снаружи.

→ [Основы](basics.ru.md#пользователь-guest)

</details>

<details><summary>9. Как включить TLS на брокере?</summary>

Слушатель `listeners.ssl.default = 5671` и `ssl_options.*` (CA, сертификат, ключ); клиент проверяет сертификат и имя хоста.

→ [Продвинутая теория](advanced.ru.md#настройка-брокера)

</details>

<details><summary>10. Подвох: клиент подключился по TLS без проверки сертификата. Защищено ли соединение?</summary>

Зашифровано, но подмена сервера возможна: проверка обязательна.

→ [Подвох 6](#6-tls-без-проверки--не-защита)

</details>

<details><summary>11. Почему Python отверг учебный CA?</summary>

В нём не было расширения `keyUsage`; строгая проверка требует его.

→ [Подвох 5](#5-python-отвергает-ca-без-keyusage)

</details>

<details><summary>12. Что делать после смены пароля пользователя?</summary>

Старый пароль перестаёт приниматься для новых соединений; открытые соединения здесь не проверялись.

→ [Продвинутая теория](advanced.ru.md#смена-пароля)

</details>

## Шпаргалка

```text
vhost + user + permissions (configure/write/read regexes on resource names)
403 ACCESS_REFUSED : bad login or no configure/write (channel) ; 530 NOT_ALLOWED : no vhost access (connection)
publish to a queue via "" needs write on amq.default
TLS: listeners.ssl.default=5671 + ssl_options.{cacertfile,certfile,keyfile}; client verifies CA and host name
```

- Минимальные права, свой vhost, свои учётные записи.
- TLS с проверкой; секреты — не в репозитории.
