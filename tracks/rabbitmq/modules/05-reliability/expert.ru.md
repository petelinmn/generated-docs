# Надёжность: экспертный уровень

🌐 **Русский** · [English](expert.en.md)

**Уровни:** [overview](overview.ru.md) · [1. Основы](basics.ru.md) · [2. Продвинутый](advanced.ru.md) · **3. Эксперт** · [4. Квиз](quiz.ru.md)

Опирается на [базовую](basics.ru.md) и [продвинутую](advanced.ru.md) теорию. «Проверено» означает наблюдалось на RabbitMQ 4.4.1 с pika 1.5.0.

## Справочник

### Что означает ответ брокера на публикацию

| Ситуация | Basic.Return | Подтверждение | Проверено |
|---|---|---|---|
| есть маршрут, сообщение принято | — | `ack` | да |
| нет маршрута, без `mandatory` | — | `ack` | да |
| нет маршрута, с `mandatory` | `312 NO_ROUTE` | `ack` (после возврата, по документации) | да |
| очередь `reject-publish` переполнена | — | `nack` | да |
| обменник не существует | канал закрыт | нет подтверждения | да |

### API pika 1.5.0 (`pika.Connection`)

| Элемент | Поведение | Проверено |
|---|---|---|
| `confirm_delivery(callback)` | включает confirms; обратный вызов получает `Basic.Ack` или `Basic.Nack` | да |
| `basic_publish(..., on_publish=f)` | `f(tag)` вызывается на потоке IOLoop после записи кадра; даёт тег подтверждения | да |
| `add_on_return_callback(f)` | `f(ch, method, props, body)` для возвращённых сообщений | да |
| `tx_select`/`tx_commit`/`tx_rollback` | у канала `pika.Connection` их нет | да |
| `multiple=True` в подтверждении | подтверждает все теги до указанного включительно | да |

### Транзакции (только `BlockingConnection`)

| Действие | Результат |
|---|---|
| публикация до `tx_commit` | сообщения не видны (глубина 0) |
| `tx_rollback` | сообщения отброшены |
| `tx_commit` | сообщения видны |

### Гарантии по звеньям

| Звено | Механизм | Если не включён |
|---|---|---|
| издатель → брокер | confirms | сообщение может потеряться без вести |
| маршрут | `mandatory` | сообщение молча отбрасывается |
| хранение | durable + persistent | исчезает при перезапуске ([модуль 03](../03-queues-and-delivery/expert.ru.md#подвохи)) |
| потребитель | ручной ack | потеря при падении |

## Внутреннее устройство

- **Подтверждения нумеруют публикации по каналу.** Тег растёт с каждой публикацией на канале с включёнными confirms; `multiple=True` схлопывает диапазон. Отсюда необходимость хранить множество неподтверждённых тегов.
- **Подтверждение не равно маршрутизации.** `ack` приходит и для сообщения, которое никуда не попало (проверено).
- **Return предшествует ack.** При `mandatory` и отсутствии маршрута сначала приходит `Basic.Return`, затем `Basic.Ack` (так сказано в документации pika; запуском проверено лишь, что приходят оба).
- **Подтверждение — свойство брокера, а не потребителя.** Оно ничего не говорит об обработке.

> ⚠️ Проверить: момент подтверждения относительно записи на диск и кворума в quorum-очередях взят из документации и здесь не проверялся.

## Подвохи

### 1. `ack` на потерянное сообщение

Сообщение без маршрута и без `mandatory` получает `ack`, но нигде не лежит (проверено).

### 2. Нет подтверждения совсем

Ошибка уровня канала (несуществующий обменник) закрывает канал, и ожидающие публикации никогда не подтвердятся. Ожидание без таймаута зависнет.

### 3. Поток IOLoop

`on_publish` выполняется на потоке IOLoop и должен возвращаться быстро; обратный вызов confirms исполняется на рабочем потоке канала. Долгая работа в них блокирует соединение.

### 4. Транзакции дороги и недоступны

100 коммитов — 4,5 с против 0,05 с на 300 сообщений с конвейерными confirms (проверено). В `pika.Connection` их нет.

### 5. Дубликаты при повторе

Повтор публикации без подтверждения может породить дубликат: первое сообщение могло дойти, а подтверждение потеряться. Нужны `message_id` и идемпотентный потребитель.

### 6. Идемпотентность в памяти

Множество `seen` в памяти теряется при перезапуске потребителя: хранение — в базе.

## Компромиссы и альтернативы

| Выбор | Плюсы | Минусы |
|---|---|---|
| Confirms по одному | просто | очень медленно (13 с на 300) |
| Конвейерные confirms | быстро | учёт тегов, повторы |
| Без confirms | максимальная скорость | потери без вести |
| Транзакции | атомарность группы | дорого, нет в новом pika |
| Outbox в базе данных | согласованность с БД | дополнительный процесс; см. [дорожную карту](../../overview.ru.md) |

## Вопросы с собеседований

<details><summary>1. Что гарантируют publisher confirms?</summary>

Что брокер принял сообщение (для persistent в durable-очереди — записал); это не значит, что оно обработано.

→ [Базовая теория](basics.ru.md#publisher-confirms)

</details>

<details><summary>2. Подвох: пришёл `ack`. Попало ли сообщение в очередь?</summary>

Не обязательно: без `mandatory` сообщение без маршрута тоже подтверждается.

→ [Подвох 1](#1-ack-на-потерянное-сообщение)

</details>

<details><summary>3. Что делает `mandatory`?</summary>

Возвращает неподходящее сообщение издателю (`Basic.Return`, 312 NO_ROUTE); подтверждение затем всё равно приходит.

→ [Базовая теория](basics.ru.md#mandatory-и-basicreturn)

</details>

<details><summary>4. Когда придёт `nack`?</summary>

Когда брокер не может принять сообщение, например `reject-publish` в переполненной очереди.

→ [Продвинутая теория](advanced.ru.md#nack-от-брокера)

</details>

<details><summary>5. Почему «один → ждём» медленно?</summary>

Каждое сообщение платит сетевую задержку; конвейер и `multiple=True` её амортизируют (13,4 с против 0,05 с на 300).

→ [Продвинутая теория](advanced.ru.md#пропускная-способность)

</details>

<details><summary>6. Подвох: как узнать, дошло ли сообщение, если канал закрылся?</summary>

Никак точно: неподтверждённые публикации «неизвестны». Их повторяют, а потребитель дедуплицирует.

→ [Продвинутая теория](advanced.ru.md#ошибки-при-которых-подтверждения-не-будет)

</details>

<details><summary>7. Чем транзакции хуже confirms?</summary>

Дороже на порядки (100 коммитов — 4,5 с), синхронны; в `pika.Connection` недоступны.

→ [Продвинутая теория](advanced.ru.md#транзакции)

</details>

<details><summary>8. Что значит доставка «минимум один раз»?</summary>

Сообщение не теряется, но может прийти дважды; нужна идемпотентность.

→ [Базовая теория](basics.ru.md#что-гарантирует-минимум-один-раз)

</details>

<details><summary>9. Как сделать потребителя идемпотентным?</summary>

Хранить обработанные `message_id` (в базе, вместе с результатом) или делать операцию идемпотентной по природе.

→ [Продвинутая теория](advanced.ru.md#идемпотентный-потребитель)

</details>

<details><summary>10. Подвох: достаточно ли persistent-сообщений для сохранности при перезапуске?</summary>

Нет: нужна ещё durable-очередь, а доставку до диска подтверждают confirms.

→ [Основы](basics.ru.md#где-сообщение-может-потеряться)

</details>

<details><summary>11. Зачем `on_publish`?</summary>

Он даёт тег публикации, по которому потом сопоставляется `ack`/`nack` из обратного вызова confirms.

→ [Справочник](#api-pika-150-pikaconnection)

</details>

<details><summary>12. Подвох: можно ли в `pika.Connection` использовать `tx_select`?</summary>

Нет, у канала нет `tx_*`; транзакции есть только в `BlockingConnection` (устарел).

→ [Справочник](#транзакции-только-blockingconnection)

</details>

## Шпаргалка

```text
publisher  : confirm_delivery(cb) + on_publish(tag) -> track tags; ack/nack/timeout
routing    : mandatory=True + add_on_return_callback  (ack comes AFTER the 312 return)
storage    : durable queue + delivery_mode=2
consumer   : manual ack after the work; idempotent by message_id (stored in the DB)
```

- Confirms плюс ack потребителя — «минимум один раз».
- `ack` не равен «есть маршрут».
- Без таймаута ждать нельзя.
