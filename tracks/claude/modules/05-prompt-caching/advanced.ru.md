# Prompt caching: продвинутый уровень

🌐 **Русский** · [English](advanced.en.md)

**Уровни:** [overview](overview.ru.md) · [1. Основы](basics.ru.md) · **2. Продвинутый** · [3. Эксперт](expert.ru.md) · [4. Квиз](quiz.ru.md)

Опирается на [базовую теорию](basics.ru.md). Код запускался против локального мок-сервера и локальных функций; настоящее поведение кэша сервиса не проверялось. Правила — со страницы документации «Prompt caching» (последняя часть страницы прочитана в сокращённом пересказе) и страницы «Cache diagnostics».

## Что ломает кэш: иерархия

Порядок префикса `tools` → `system` → `messages` задаёт, что именно сбрасывается:

| Изменение | tools | system | messages |
|---|---|---|---|
| Определения инструментов (имя, описание, параметры) | сброс | сброс | сброс |
| Включение/выключение web search или цитат | сохр. | сброс | сброс |
| `speed` (быстрый или обычный режим) | сохр. | сброс | сброс |
| `tool_choice` | сохр. | сохр. | сброс |
| Добавление/удаление изображений где угодно | сохр. | сохр. | сброс |
| Параметры мышления, `output_config.effort` | зависит от модели | зависит от модели | сброс |

Чем выше по префиксу изменение, тем больше сбрасывается. Отсюда правило архитектуры: **самое стабильное — в начало** (инструменты, затем `system`), переменное — в конец.

## Стабильный префикс: чек-лист

- В начале нет **времени, дат, UUID, счётчиков**: достаточно одного изменённого байта, и префикс другой. В проверке на хэшах строка с меняющейся секундой дала разные отпечатки (`False`), а неизменная — одинаковые (`True`).
- Порядок инструментов и **ключей JSON** детерминирован: в опыте `json.dumps({"b": 1, "a": 2})` и `json.dumps({"a": 2, "b": 1})` дали разные строки (`False`), а с `sort_keys=True` — одинаковые. Это касается и ключей во входных данных инструментов: в некоторых языках (Swift, Go) порядок ключей случаен.
- Набор инструментов не меняется между запросами; нужный инструмент включайте через инструкцию, а не через смену списка.
- Операторские инструкции в ходе диалога добавляйте сообщением `{"role": "system"}` в `messages` на моделях, которые это поддерживают, а не правкой верхнего `system`.
- Не переключайтесь между режимами (`speed`, мышление, схема `output_config.format`) без необходимости: смена сбрасывает кэш.

## Порядок и смешивание TTL

Можно использовать точки с разным TTL, но **длинный TTL должен идти раньше короткого**: 1-часовая запись ставится перед любой 5-минутной.

```python
def valid_ttl_order(blocks):
    seen_5m = False
    for ttl in blocks:
        if ttl == "5m": seen_5m = True
        elif ttl == "1h" and seen_5m: return False
    return True
print(valid_ttl_order(["1h", "5m"]), valid_ttl_order(["5m", "1h"]), valid_ttl_order(["1h", "1h", "5m"]))
```

```text
True False True
```

Оплата: чтение для части до последнего попадания; 1-часовая запись — для токенов между последним попаданием и последней 1-часовой точкой; 5-минутная запись — для остального. Запрос, прочитавший 5-минутную запись, **продлевает** её 5-минутное время жизни, даже если у него указан `"ttl": "1h"`. Время жизни считается от **начала** запроса.

## Прогрев кэша: max_tokens: 0

Чтобы записать кэш заранее (например, до пика нагрузки), отправьте запрос с `max_tokens: 0`: запись произойдёт без генерации.

```python
r = client.messages.create(model="claude-opus-5-5", max_tokens=0, cache_control={"type": "ephemeral"},
                           system=BIG_SYSTEM, messages=[{"role": "user", "content": "x"}])
print(r.content, r.stop_reason, r.usage.output_tokens, r.usage.cache_creation_input_tokens)
```

```text
[] max_tokens 0 2048
```

Ответ — пустой `content`, `stop_reason: "max_tokens"`, ноль выходных токенов (значения вернул мок; SDK 2.13.0 принял `max_tokens=0`). Правила прогрева: точка должна стоять на **последнем общем блоке** с рабочими запросами; настройки мышления и `effort` — те же; прогрев, который пишет, оплачивается как запись. Запрос отклоняется (`invalid_request_error`) при `stream: true`, `thinking.type: "enabled"`, `output_config.format`, принудительном `tool_choice` и в пакетах Message Batches.

## Параллельные запросы

Запись в кэше **становится доступной только после начала первого ответа**. Если запустить сто запросов одновременно, они все могут записать кэш, а не прочитать его. Решение: отправить один запрос (или прогрев), дождаться начала ответа и только потом запускать остальные. Для пакетов (Message Batches) попадания — «по возможности».

## Инструменты, мышление, документы

- **Инструменты:** `cache_control` ставят на последний инструмент; всё, что до него, кэшируется одним префиксом.
- **Мышление:** блоки `thinking` нельзя пометить `cache_control` напрямую; они кэшируются вместе с остальным содержимым в следующих ходах, а при чтении из кэша считаются входными токенами.
- **Документы и изображения** из сообщений пользователя можно кэшировать; для цитат кэшируйте документ верхнего уровня.
- **Пустые текстовые блоки** кэшировать нельзя.

## Окно просмотра

Система проверяет не более 20 позиций для каждой точки (сама точка — первая); серия подряд идущих `tool_use` считается одной позицией, как и серия `tool_result`. В очень длинных диалогах расставляйте точки так, чтобы последнее попадание оставалось в окне просмотра (автоматический режим делает это за вас).

## Диагностика промахов

Страница «Cache diagnostics» описывает поле `diagnostics`: в запросе — `"diagnostics": {"previous_message_id": null}` для первого хода и `id` предыдущего ответа для следующих; в ответе — `diagnostics` с `cache_miss_reason`, где `type` бывает `model_changed`, `system_changed`, `tools_changed`, `messages_changed`, `previous_message_not_found`, `unavailable`. Так можно понять, **что именно** изменилось.

> ⚠️ Проверить: имя бета-заголовка и доступность диагностики на каждой модели и платформе в этом материале не проверялись; страница указывает статус `stable`, примеры используют `client.beta.messages`.

## Изоляция

Организации никогда не делят кэш. На Claude API, Claude Platform on AWS и Foundry действует изоляция по рабочему пространству; на Amazon Bedrock и Google Cloud (Google managed) — только по организации.

## Лучшие практики

- Стабильное — в начало, переменное — в конец.
- Автоматический `cache_control` для диалогов; явные точки — для разной «температуры» частей.
- Проверять `usage` при каждом изменении промпта.
- Прогревать кэш перед пиком и не запускать параллельные запросы «вхолодную».
- Не менять инструменты, `speed`, мышление и схему без нужды.
- 1-часовой TTL — если запросы идут реже, чем раз в 5 минут.

## Частые ошибки

- ❌ `datetime.now()` в `system` → ✅ время в последнее сообщение.
- ❌ Недетерминированный порядок инструментов/ключей → ✅ сортировка.
- ❌ 5-минутная точка раньше 1-часовой → ✅ длинный TTL ставят раньше короткого.
- ❌ Сто параллельных запросов с одним новым префиксом → ✅ прогрев и ожидание.
- ❌ Смена `speed` или схемы между запросами → ✅ зафиксировать.
- ❌ Ждать кэширования короткого префикса → ✅ проверить минимум модели.
