# Схемы и сериализация

🌐 **Русский** · [English](overview.en.md)

## Коротко

Kafka хранит байты, поэтому формат записей — договорённость производителей и потребителей. Схему (например, **Avro**) описывают явно, а **Schema Registry** хранит схемы, выдаёт им номера и проверяет **совместимость** новых версий. В записи идут магический байт, номер схемы и данные.

## Ключевые идеи

- **Avro компактнее JSON:** 16 байт против 50 (без схемы).
- **Формат записи:** `0x00` + идентификатор схемы (4 байта) + данные Avro.
- **Субъект по умолчанию:** `<тема>-value`.
- **`BACKWARD` (по умолчанию):** новый читатель читает старые данные; новое поле — со значением по умолчанию, иначе `409`.
- **Читатели:** на старой схеме игнорируют новые поля, на новой подставляют умолчание в старых записях.
- **Переименование и смена типа** несовместимы; алиас пропускает переименование.
- **`auto.register.schemas`:** в рабочей системе отключайте.
- **Реестр — отдельный сервис Confluent,** а не часть Kafka.

## Минимальный пример

```python
ser = AvroSerializer(sr, schema_str)
payload = ser(record, SerializationContext("orders", MessageField.VALUE))
producer.produce("orders", value=payload)
```

Всё запускалось на настоящих Apache Kafka 4.3.1 и Schema Registry 8.4.1 в Docker (см. [базовую теорию](basics.ru.md)).

## Когда применять и когда нет

| Задача | Выбор |
|---|---|
| Много потребителей и эволюция формата | Avro + реестр |
| Быстрый прототип, один потребитель | JSON без схемы (осознавая риск) |
| Централизованная проверка совместимости | реестр и CI |

- ❌ Не меняйте формат без проверки совместимости.
- ❌ Не оставляйте автоматическую регистрацию в рабочей системе.
