# Темы, хранение и компактация: продвинутый уровень

🌐 **Русский** · [English](advanced.en.md)

**Уровни:** [overview](overview.ru.md) · [1. Основы](basics.ru.md) · **2. Продвинутый** · [3. Эксперт](expert.ru.md) · [4. Квиз](quiz.ru.md)

Опирается на [базовую теорию](basics.ru.md) (тот же брокер с ускоренными проверками). Код запускался на Apache Kafka 4.3.1 с `confluent-kafka` 2.16.2.

## Компактация журнала

Политика `cleanup.policy=compact` хранит не «записи за период», а **последнее значение каждого ключа**: старые записи с тем же ключом удаляются. Так хранят состояние (профиль пользователя, настройки), а не историю событий.

Тема с `cleanup.policy=compact`, `segment.ms=1000`, `min.cleanable.dirty.ratio=0.01`. Три ключа обновлены четыре раза (12 записей):

```text
before: 12 records
after compaction: [(9, 'k1', 'k1-v3'), (10, 'k2', 'k2-v3'), (11, 'k3', 'k3-v3'), (12, 'k9', 'roll'), (13, 'k9', 'roll2')]
```

- Осталось по одной последней записи для `k1`, `k2`, `k3` (`v3`).
- **Смещения сохранились** (9, 10, 11): в нумерации появились пропуски, но у записи прежний номер.
- Две записи ключа `k9` остались обе. Вероятная причина: они лежали в **активном** сегменте, а по документации чистятся только закрытые сегменты (после следующих записей `roll` и `roll2` в итоге исчезли — см. ниже).

Чтение по-прежнему идёт по возрастанию смещений; потребитель просто не видит удалённых значений.

### Могильные записи (tombstones)

Чтобы удалить ключ, публикуют запись с этим ключом и **пустым значением** (`None`) — tombstone:

```python
p.produce("cmp", key=b"k2", value=None)
```

```text
tombstone present: [(14, 'k2', None)]
after delete.retention.ms: [(14, 'k2', None)] all: [(9, 'k1', 'k1-v3'), (11, 'k3', 'k3-v3'), (14, 'k2', None), (15, 'k9', 'roll3'), (16, 'k9', 'roll4')]
```

Старое значение `k2` (смещение 10) исчезло, остался tombstone (смещение 14). Брокер удаляет и сам tombstone по истечении `delete.retention.ms` (в опыте 3 секунды); в наших замерах он остался и через ~20 с: очистка выполняется только для закрытых сегментов, и этот tombstone лежал в активном.

> ⚠️ Проверить: когда именно брокер удаляет tombstone (после очередной очистки сегмента с ним и по истечении `delete.retention.ms`) здесь не доказано: наблюдалось лишь, что он пережил ~20 с.

Потребителям нужно уметь обрабатывать `value is None` как «ключ удалён».

## Компактация или срок хранения

| Нужно | Политика |
|---|---|
| история событий за период | `delete` (по сроку/размеру) |
| текущее состояние по ключу | `compact` |
| и то и другое | `compact,delete` |

> ⚠️ Проверить: значение `compact,delete` и параметры `min.compaction.lag.ms`, `max.compaction.lag.ms` здесь не проверялись (задавался только `min.compaction.lag.ms=0`).

## Добавление партиций и ключи

Число партиций можно увеличить. Но записи с одним ключом могут начать попадать в **другую** партицию:

```text
old producer after 3->6: True | new producer moved keys: {'user0': (2, 5), 'user2': (2, 5), 'user3': (2, 5), 'user5': (1, 4)}
```

Опыт: тема из 3 партиций, 8 ключей; партиции увеличили до 6.

- **Новый** производитель отправил четыре ключа в другие партиции (`user0`: 2 → 5 и т. д.), остальные четыре остались.
- **Старый** производитель (создан до увеличения) продолжил писать по старой схеме: он не узнал о новых партициях, потому что обновляет метаданные не сразу (параметр `topic.metadata.refresh.interval.ms`, по документации librdkafka 5 минут).

Следствие: порядок записей одного ключа ломается — старые записи в старой партиции, новые — в другой, и потребители могут увидеть их не по порядку. Поэтому число партиций планируют заранее ([модуль 01](../01-kafka-basics/expert.ru.md#1-партиции-нельзя-уменьшить)).

> ⚠️ Проверить: значение `topic.metadata.refresh.interval.ms` по умолчанию взято из документации librdkafka и здесь не проверялось; наблюдалось лишь, что производитель, созданный до увеличения, не перешёл на новые партиции в течение опыта.

## Лучшие практики

- Выберите политику под данные: события — `delete`, состояние — `compact`.
- Задавайте `retention.ms` явно и держите запас относительно скорости потребителей.
- Не считайте последнюю запись «вечной»: сегменты удаляются целиком.
- Планируйте число партиций с запасом; увеличение ломает порядок по ключам.
- Для compact-тем обрабатывайте tombstone (`value is None`).
- Не меняйте политики на рабочей теме без проверки: удалённое не вернуть.

## Частые ошибки

- ❌ `compact` для истории событий → ✅ она хранит только последнее значение ключа.
- ❌ Ожидать компактации мгновенно → ✅ она выполняется фоном, и не для активного сегмента.
- ❌ Не обрабатывать `None` в compact-теме → ✅ это удаление ключа.
- ❌ Добавлять партиции «на лету» → ✅ ключи сменят партиции.
