# Rate limiting: масштаб и грани

**Пререквизиты:** [минимум](basics.ru.md) и [production](advanced.ru.md). **Время:** ~30 мин.

## Масштаб: несколько экземпляров

Встроенные лимитеры хранят счётчики **в памяти процесса**. При N экземплярах за балансировщиком реальный лимит клиента — до N × лимит (или меньше при «липких» сессиях). Решения:

- **Лимит на входе:** API-шлюз/балансировщик/CDN (nginx, Envoy, YARP, облачные шлюзы) считает централизованно; приложение — запасной уровень.
- **Общее хранилище счётчиков** (Redis с атомарными операциями/скриптами): точный лимит, но дополнительный сетевой вызов на запрос и новая точка отказа — решите, что делать при недоступности хранилища (fail-open или fail-closed).
- **Деление лимита** между экземплярами (лимит/N): приблизительно и просто.

Встроенный middleware даёт только локальную защиту экземпляра — этого достаточно как «предохранитель» от перегрузки, но не как точная квота клиента.

## Грани и подвохи

**1. Стык окон fixed window.** Клиент может сделать N запросов в конце одного окна и N в начале следующего — 2N за короткое время (sliding window/token bucket сглаживают).

**2. Порядок параллельных запросов.** Из 5 одновременных запросов при лимите 3 отказ получили два, но какие именно — не определено (проверено: `429 200 200 429 200`).

**3. IP за прокси.** Без `UseForwardedHeaders` все клиенты имеют адрес прокси и делят один лимит.

**4. Партиции растут.** Каждый ключ — отдельный лимитер в памяти; миллионы уникальных ключей (случайные значения от атакующего) — утечка памяти; ограничивайте ключи (аутентифицированные пользователи) и завязывайте на TTL.

**5. Очередь удерживает ресурсы.** Большой `QueueLimit` занимает соединения/потоки.

**6. 429 не должен ломать инфраструктуру.** Health checks и метрики исключите из лимитов.

**7. Стоимость запроса неодинакова.** Один дорогой запрос лучше считать за несколько «токенов» (token bucket с переменным числом токенов) или отдельной политикой.

**8. Клиентская сторона.** Клиенты должны уважать `Retry-After` и использовать экспоненциальную задержку с джиттером (см. [Устойчивый HttpClient](../http-client-resilience/overview.ru.md)).

## Альтернативы и дополнения

| Подход | Для чего |
|---|---|
| Встроенный `AddRateLimiter` | локальная защита экземпляра |
| API-шлюз (YARP, Envoy, облако) | централизованные квоты, ключи API |
| Redis-лимитер | точные распределённые лимиты |
| Кэширование | меньше запросов к бэкенду без отказов |
| Backpressure (очереди, `Channel<T>`) | сглаживание внутри системы |
| Bulkhead (изоляция пулов) | отказ одной части не топит остальные |

## Вопросы с собеседований

<details><summary>1. Зачем нужен rate limiting?</summary>

Защита от перебора, злоупотреблений и перегрузки; справедливое распределение ресурсов; соблюдение квот тарифов.

</details>

<details><summary>2. Какие алгоритмы вы знаете и чем они отличаются?</summary>

Fixed window (просто, всплеск на стыке), sliding window (сглаживает), token bucket (допускает всплеск при ограниченной средней скорости), concurrency (ограничение одновременных), leaky bucket (постоянная скорость).

</details>

<details><summary>3. Какой код ответа и какие заголовки при превышении?</summary>

429 Too Many Requests и `Retry-After` (когда повторить). Проверено: ответ с `Retry-After`.

</details>

<details><summary>4. Как ограничивать по пользователю?</summary>

Через разбиение (`RateLimitPartition`) по ключу — пользователь, API-ключ, IP; у каждого ключа отдельный счётчик (проверено: `ann` отклонён, `bob` проходит).

</details>

<details><summary>5. В чём проблема in-memory лимитов при нескольких экземплярах?</summary>

Каждый экземпляр считает отдельно: общий лимит клиента до N × лимит. Нужны центральный шлюз или общее хранилище (Redis).

</details>

<details><summary>6. Fixed window и sliding window: в чём разница?</summary>

Fixed считает по неподвижным окнам и допускает до 2N на стыке; sliding делит окно на сегменты и сдвигает его — более ровное ограничение.

</details>

<details><summary>7. Как работает token bucket?</summary>

Ведро ёмкости B пополняется со скоростью r; запрос забирает токен. Допускает всплеск до B, но средняя скорость ≤ r (проверено на ёмкости 2, +1/с).

</details>

<details><summary>8. Для чего concurrency limiter?</summary>

Ограничивает число одновременных запросов (тяжёлые операции). Проверено: из трёх одновременных медленных запросов прошёл один.

</details>

<details><summary>9. Вопрос с подвохом: лимит 3 в секунду, но клиент делает 6 запросов за короткое время без отказов. Как?</summary>

Стык окон fixed window (3 в конце окна + 3 в начале следующего) либо несколько экземпляров с независимыми счётчиками.

</details>

<details><summary>10. Вопрос с подвохом: все пользователи за корпоративным прокси делят один лимит. Почему?</summary>

Ключ — IP, а он у всех один; нужен ключ по пользователю или корректные forwarded headers.

</details>
