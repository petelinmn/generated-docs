## Checking the file type

The client specifies the name and `Content-Type` itself — they cannot be trusted. The minimum:

1. an allow-list of extensions;
2. a check of the content's "magic bytes";
3. a size limit.

```csharp
app.MapPost("/sniff", async (IFormFile file) =>
{
    var allowed = new[] { ".png", ".jpg", ".txt" };
    var ext = Path.GetExtension(file.FileName).ToLowerInvariant();
    if (!allowed.Contains(ext)) return Results.BadRequest("extension not allowed");
    var head = new byte[4];
    await using var s = file.OpenReadStream();
    await s.ReadExactlyAsync(head);
    var isPng = head.AsSpan().SequenceEqual(new byte[] { 0x89, 0x50, 0x4E, 0x47 });
    return ext == ".png" && !isPng ? Results.BadRequest("content is not PNG") : Results.Ok("ok");
}).DisableAntiforgery();
```

Verified: `x.exe` → `extension not allowed`; `x.png` with arbitrary bytes → `content is not PNG`; a real PNG signature → `ok`. This is first-level protection: for critical cases (images, documents) use parsing libraries and antivirus scanning.

> ⚠️ Verify: the full set of format signatures and recommendations on scanning for malicious content were not run in this material.

## Antiforgery

`IFormFile` endpoints in Minimal API require an antiforgery token by default. Verified: with `AddAntiforgery()` + `UseAntiforgery()` a form without a token → `400`, while an endpoint with `DisableAntiforgery()` → `200`. For browser forms keep the check on and hand out the token through `IAntiforgery`; disable it only for APIs authenticated by a header (a token, not a cookie) — CSRF does not apply there.

## Streaming multipart upload

`IFormFile` buffers the form (memory or a temporary file). For very large files read the multipart as a stream:

```csharp
var boundary = HeaderUtilities.RemoveQuotes(MediaTypeHeaderValue.Parse(req.ContentType).Boundary).Value!;
var reader = new MultipartReader(boundary, req.Body);
while (await reader.ReadNextSectionAsync() is { } section)
{
    var cd = ContentDispositionHeaderValue.Parse(section.ContentDisposition);
    // copy section.Body to the destination stream
}
```

Verified: a form with two files (`a.bin` — 1000 bytes, `b.bin` — 50 bytes) was read section by section: `f1:a.bin:1000;f2:b.bin:50`. The types `MediaTypeHeaderValue`/`ContentDispositionHeaderValue` here are from `Microsoft.Net.Http.Headers` (not from `System.Net.Http.Headers`; with both `using`s there is an ambiguity, compile error CS0104).

## Path safety and storage

| Rule | Why |
|---|---|
| The on-disk name is generated by the server | path traversal, overwriting others' files |
| `Path.GetFileName` for any client name | drops the directory part (verified) |
| Store outside the web root | the file is not executed or served directly |
| Serve with `Content-Disposition: attachment` and a safe type | protection from XSS through uploaded HTML/SVG |
| Check download permissions | do not serve others' files by a guessed id |
| A size limit and per-user quotas | protection from filling the disk |

In the cloud files go to object storage (Azure Blob, S3): the server hands the client a short-lived signed link, and the file bypasses your API.

> ⚠️ Verify: cloud SDK APIs (Azure Blob/S3) and signed links were not run in this material.

## Client errors and responses

| Situation | Response |
|---|---|
| no `file` part | `400` (verified) |
| body larger than the limit | `413` (verified) |
| extension/content not allowed | `400`/`415` |
| file not found | `404` (verified) |
| no permission | `403` |

## Best practices

| Rule | Why |
|---|---|
| Streaming copy | memory does not grow with file size |
| An allow-list of types + content check | the client's type is untrustworthy |
| Server names and a directory outside the web root | path safety |
| Limits on the body, forms and quotas | protecting resources |
| Asynchronous I/O and a `CancellationToken` | no blocked thread, client abort |
| Metadata (name, type, size, owner) in the DB | search and permissions |
