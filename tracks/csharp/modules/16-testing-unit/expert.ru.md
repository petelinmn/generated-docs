# Unit-тесты: экспертная теория

🌐 **Русский** · [English](expert.en.md)

**Уровни:** [обзор](overview.ru.md) · [1. Базовая](basics.ru.md) · [2. Продвинутая](advanced.ru.md) · **3. Экспертная** · [4. Квиз](quiz.ru.md)

**Пререквизиты:** [базовая](basics.ru.md) и [продвинутая](advanced.ru.md) теория. **Время:** ~1 ч.

## Как это устроено

**xUnit v3** — тестовые проекты теперь самостоятельные исполняемые файлы (`OutputType=Exe`) со встроенным хостом, который реализует **Microsoft.Testing.Platform** (MTP): обнаружение тестов, запуск, фильтры, расширения (покрытие, отчёты) и коды завершения. `dotnet test` запускает этот исполняемый файл и разбирает его вывод; в `global.json` нужен режим `"runner": "Microsoft.Testing.Platform"` — без него v3 в .NET 10+ SDK не запускается. Код завершения при падении тестов — 2 (проверено), успех — 0.

**Жизненный цикл теста.** Для каждого теста xUnit: создаёт экземпляр тестового класса (конструктор → при необходимости `InitializeAsync`) → вызывает метод → `DisposeAsync`/`Dispose`. Фикстуры класса и коллекции создаются раньше первого теста и освобождаются после последнего. Параметры теории — отдельные тест-кейсы с собственными экземплярами.

**Параллельность.** Единица параллельности — **тестовая коллекция**; по умолчанию это класс. Классы выполняются параллельно, тесты внутри класса — последовательно. Проверено: три класса с одновременно стартующими тестами достигли 3 одновременных исполнений. Следствие: **статическое состояние общее для всех параллельных тестов**.

## Утверждения и их семантика

- **Точное совпадение типа.** `Assert.Throws<Exception>(...)` для `InvalidOperationException` **падает** («Exception type was not an exact match»); `Assert.ThrowsAny<Exception>(...)` — проходит (проверено).
- **Порядок коллекций.** `Assert.Equal(new[]{1,2}, new[]{2,1})` падает («Collections differ»); сравнение без учёта порядка — `Assert.Equivalent` (проверено: проходит).
- **Асинхронный код.** `Assert.Throws<T>(() => throw …)` с лямбдой, которую компилятор привязывает к `Func<Task>`, — ошибка компиляции `CS0619`: «You must call Assert.ThrowsAsync<T> (and await the result) when testing async code». Для асинхронного кода — `ThrowsAsync` с `await`; для синхронного — лямбда-`Action` или группа методов (проверено).
- **Условный пропуск во время выполнения.** `Assert.Skip("причина")` прерывает тест как пропущенный (проверено: `пропущено … not on this OS`); `[Fact(Skip = …)]` — безусловный.
- **Сравнение вещественных.** Только с точностью (`precision`) или допуском.
- **Сообщения.** Для строк указывается позиция первого различия, для коллекций — оба списка (проверено).

## Справочник

| Что | API xUnit v3 |
|---|---|
| Тест | `[Fact]`, `[Fact(Skip = "…")]`, `Assert.Skip(…)` |
| Параметризация | `[Theory]`, `[InlineData]`, `[MemberData]`, `[ClassData]`, `TheoryData<…>` |
| Общее состояние | `IClassFixture<T>`, `ICollectionFixture<T>`, `[Collection]`, `IAsyncLifetime` |
| Метки и фильтры | `[Trait]`, `--filter-trait`, `--filter-method`, `--filter-class`, `--filter-namespace` |
| Контекст теста | `TestContext.Current` (`CancellationToken`, вывод, статус) |
| Проверки | `Equal`, `Equivalent`, `Throws`/`ThrowsAny`/`…Async`, `Collection`, `All`, `Single`, `Contains`, `Raises` |
| Параллельность | `[assembly: CollectionBehavior(...)]`, `DisableParallelization` |
| Покрытие | `Microsoft.Testing.Extensions.CodeCoverage` (`--coverage`) |

## Подвохи

**1. Статическое состояние и параллельность.** Два теста, увеличивающие общий статический счётчик, даже по отдельности корректны, но вместе один падает (проверено: `Actual: 2`). Не используйте статику в тестах; если неизбежно — коллекция без параллельности.

**2. Исключение без `ThrowsAny`.** `Throws<Exception>` не ловит наследников.

**3. `async void` тесты** не ожидаются — тест «проходит» до завершения. Только `async Task`.

**4. Зависимость от порядка.** Тесты в классе не гарантируют порядок, поэтому зависеть друг от друга нельзя.

**5. Тест, который не может упасть.** Без `Assert` или с проверкой, истинной по построению, тест бесполезен. Помогает мутационное тестирование (Stryker.NET).

**6. Покрытие ≠ качество.** 100% строк можно покрыть тестами без проверок.

**7. Перебор моков.** Тест, проверяющий каждый внутренний вызов, ломается при любом рефакторинге.

**8. Внешняя среда.** Часы, случайность, файловая система, переменные окружения, культура: `ToString()` числа зависит от текущей культуры — тест, сравнивающий строки, падает на другой локали.

## Компромиссы и альтернативы

| Подход | Плюсы | Минусы |
|---|---|---|
| xUnit | стандарт сообщества, изоляция по умолчанию, расширяемость | инстанс на тест непривычен после NUnit |
| NUnit / MSTest | привычные `[SetUp]`, богатые атрибуты | общее состояние по умолчанию |
| Ручные дублёры (fakes) | простые, прозрачные | много кода |
| NSubstitute / Moq | быстро создают дублёры | риск перебора проверок вызовов |
| Property-based (FsCheck) | находит неожиданные входы | нужна культура свойств |
| Мутационное тестирование (Stryker.NET) | проверяет качество тестов | долго работает |

## Вопросы с собеседований

<details><summary>1. Чем unit-тест отличается от интеграционного?</summary>

Unit-тест проверяет единицу кода изолированно (зависимости заменены дублёрами), быстр и детерминирован. Интеграционный проверяет взаимодействие реальных компонентов (БД, HTTP) и медленнее ([17](../17-testing-integration/overview.ru.md)).

</details>

<details><summary>2. Что такое Arrange-Act-Assert?</summary>

Структура теста: подготовка данных и объектов, вызов проверяемого кода, проверка результата. Делает тест читаемым и выделяет, что именно проверяется.

</details>

<details><summary>3. Чем `[Fact]` отличается от `[Theory]`?</summary>

`Fact` — тест без параметров; `Theory` — параметризованный, выполняется для каждой строки данных (`InlineData`, `MemberData`, `ClassData`); каждая строка — отдельный тест-кейс.

</details>

<details><summary>4. Как xUnit изолирует тесты?</summary>

Создаёт новый экземпляр тестового класса для каждого теста (проверено: два теста, каждый увеличивает поле, видят `1`). Общее состояние — только явно, через фикстуры.

</details>

<details><summary>5. Что такое фикстура и какие бывают?</summary>

Общий объект для нескольких тестов. `IClassFixture<T>` — один на класс; `ICollectionFixture<T>` — на коллекцию; для каждого теста — конструктор/`Dispose`. Асинхронная подготовка — `IAsyncLifetime`.

</details>

<details><summary>6. Что такое stub, fake и mock?</summary>

Stub возвращает заданные значения; fake — рабочая упрощённая реализация; mock запоминает вызовы и позволяет проверить взаимодействие.

</details>

<details><summary>7. Как тестировать код, зависящий от времени?</summary>

Вводить время через интерфейс (`IClock`, `TimeProvider`) и подставлять фиксированное значение; не использовать `DateTime.Now` напрямую.

</details>

<details><summary>8. Как xUnit параллелит тесты?</summary>

Классы (тестовые коллекции) выполняются параллельно, тесты внутри класса — последовательно. Общее статическое состояние опасно; ресурсы объединяют в одну коллекцию.

</details>

<details><summary>9. Почему `Assert.Throws<Exception>` может не сработать?</summary>

Он требует точного типа; для наследников нужен `ThrowsAny`. Проверено: для `InvalidOperationException` с `Throws<Exception>` — «not an exact match».

</details>

<details><summary>10. Что такое покрытие кода и можно ли ему доверять?</summary>

Доля выполненных строк/ветвей. Показывает, что не тестируется, но не качество проверок: можно выполнить код и ничего не проверить.

</details>

<details><summary>11. Вопрос с подвохом: два корректных теста падают вместе. Почему?</summary>

Вероятно, общее статическое состояние: тесты разных классов (или порядок внутри класса) мешают друг другу. Проверено: два теста с общим статическим счётчиком — один падает.

</details>

<details><summary>12. Вопрос с подвохом: тест `async void` показывает «успех», хотя внутри исключение. Почему?</summary>

`async void` нельзя ожидать — исключение не передаётся раннеру, тест завершается раньше. Нужно `async Task`.

</details>

<details><summary>13. Вопрос с подвохом: покрытие 0%, хотя тесты прошли. Почему?</summary>

Покрытие считается по сборкам, отличным от тестовой. Если проверяемый код лежит в самом тестовом проекте, отчёт пуст (проверено: `<packages />`).

</details>
