# Наблюдаемость: экспертная теория

🌐 **Русский** · [English](expert.en.md)

**Уровни:** [обзор](overview.ru.md) · [1. Базовая](basics.ru.md) · [2. Продвинутая](advanced.ru.md) · **3. Экспертная** · [4. Квиз](quiz.ru.md)

**Пререквизиты:** [базовая](basics.ru.md) и [продвинутая](advanced.ru.md) теория. **Время:** ~1 ч.

## Модель «источник — слушатель»

Платформа .NET отделяет **излучение** сигналов от их **сбора**. Код создаёт `ActivitySource` и `Meter` и пишет в них всегда; есть ли кто-то, кому эти данные нужны, решают **слушатели**: `ActivityListener` (трассы), `MeterListener` (метрики), провайдеры `ILogger`. SDK OpenTelemetry — просто сложный слушатель.

- **Нулевая стоимость без слушателя.** Пока слушателя нет, `StartActivity` возвращает `null` (проверено), а `Counter.Add` — почти пустая операция. Поэтому в библиотеках без раздумий добавляют инструментацию.
- **Подписка по имени.** Слушатель выбирает источники по имени (`ShouldListenTo`, `AddSource("Demo.Shop")`, `AddMeter`). Забытый `AddSource` — частая причина «спанов нет».
- **Решение о записи** принимает `Sample` слушателя. Проверено: `None` → `null`; `PropagationData` → активность создана, но данные не собираются (`IsAllDataRequested = False`); `AllData` → `IsAllDataRequested = True`; `AllDataAndRecorded` → ещё и `Recorded = True` (флаг записи, который передаётся в `traceparent` как `01`).
- **`Activity.Current`** хранится в `AsyncLocal`, поэтому течёт через `await` и `Task.Run` ([10 · Async/await](../10-async-await/expert.ru.md#контекст-выполнения-executioncontext-и-asynclocalt)); дочерние спаны получают родителя неявно. После `await` в «чужом» потоке (например, через собственный пул) контекст может потеряться.
- **`MeterListener`** получает измерения синхронно в потоке записавшего (проверено: `shop.orders=1 [region:eu]` прилетело внутри `Add`); `ObservableGauge` опрашивается при `RecordObservableInstruments()`. Поэтому обратные вызовы должны быть быстрыми и потокобезопасными.

## Тонкости данных

- **`Tags` и `TagObjects`.** `SetTag("order.id", 42)` кладёт значение типа `Int32` в `TagObjects`, а `Tags` содержит только строковые теги (проверено). Экспортёры используют `TagObjects`.
- **Кардинальность метрик.** Каждая уникальная комбинация значений тегов — отдельный временной ряд; `user_id` порождает миллионы рядов, и бэкенд падает. Большие идентификаторы кладут в **трассы и логи**, а не в теги метрик.
- **Агрегация.** Счётчики и гистограммы на стороне SDK агрегируются за интервал (кумулятивно или дельтой); сырые измерения не хранятся. Для гистограмм важны границы корзин (buckets): подберите под ожидаемые задержки.
- **Exemplars.** Образцы связывают точку метрики с конкретной трассой — переход «выброс на графике → трасса».
- **Baggage** — пары «ключ-значение», путешествующие вместе с контекстом (заголовок `baggage`); расходует трафик и может утечь — не кладите секреты.

## Выборка (sampling)

| Вид | Как работает | Плюсы | Минусы |
|---|---|---|---|
| Head (в начале) | решение при создании корневого спана, наследуется (`ParentBased`) | дёшево, просто | можно пропустить интересные ошибки |
| Tail (в конце) | коллектор видит всю трассу и сохраняет ошибочные/медленные | сохраняет важное | нужен буфер и состояние на коллекторе |
| По доле (`TraceIdRatioBased`) | детерминированно по `TraceId` | одинаково на всех сервисах | не учитывает «важность» |

Решение должно приниматься **согласованно** на всех сервисах — иначе трассы окажутся рваными: родительское решение передаётся флагами в `traceparent`.

## SLI, SLO и алерты

- **SLI** — измеримый показатель качества (доля успешных запросов, p95 задержки); **SLO** — цель по SLI («99,9% успешных за 30 дней»); **бюджет ошибок** — допустимая доля сбоев, которой управляют темпом изменений.
- Алертят по **симптомам, которые видит пользователь** (ошибки, задержка, насыщение), а не по каждой внутренней причине: меньше шума. Методики: RED (rate, errors, duration — для сервисов), USE (utilization, saturation, errors — для ресурсов), «четыре золотых сигнала».
- Алерт должен быть **действенным**: человек знает, что делать; иначе его отключают.

## Диагностика процесса

Помимо OpenTelemetry, в .NET есть низкоуровневые средства: **EventPipe/EventSource** (счётчики и события runtime: GC, пул потоков, аллокации) читаются через `dotnet-counters`/`dotnet-trace`; дампы (`dotnet-dump`) и профилировщики дают картину «внутри процесса» ([19 · Производительность](../19-performance/overview.ru.md)). Метрики OpenTelemetry показывают симптом на уровне сервиса, а профилировщик — причину в коде.

> ⚠️ Проверить: команды `dotnet-counters`, `dotnet-trace`, `dotnet-dump` в этом материале не запускались (инструменты не устанавливались); сверьтесь с документацией перед использованием.

## Подвохи

**1. `StartActivity` возвращает `null`.** Без слушателя или при `None`: пишите `a?.SetTag(...)` (проверено).

**2. Забыли `AddSource`/`AddMeter`.** Данные излучаются, но SDK их не слушает.

**3. `Tags` не показывает нестроковые теги** (проверено) — смотрите `TagObjects`.

**4. Высокая кардинальность тегов** разоряет бэкенд метрик.

**5. Liveness с зависимостями.** Падение БД перезапускает все экземпляры приложения; liveness должен проверять только процесс.

**6. `Degraded` — это 200 по умолчанию** (проверено): оркестратор не убирает экземпляр из балансировки; для 503 меняют `ResultStatusCodes`.

**7. Потеря контекста.** Свой поток/пул без `Activity.Current` рвёт трассу; инструментируйте брокеры и фоновые задачи вручную.

**8. Секреты и PII в тегах/логах** попадают во внешние системы.

**9. Тяжёлые обработчики `MeterListener`/`ObservableGauge`** тормозят приложение, так как выполняются синхронно.

## Компромиссы и альтернативы

| Подход | Плюсы | Минусы |
|---|---|---|
| OpenTelemetry + OTLP | стандарт, любой бэкенд | нужно настроить коллектор и бэкенд |
| Vendor SDK (Application Insights, Datadog) | богатые интеграции «из коробки» | привязка к поставщику |
| Только логи | просто | нет метрик и сквозных трасс |
| Prometheus + Grafana, Jaeger/Tempo, Loki | открытый стек | эксплуатировать самим |
| Профилировщик по требованию | причина в коде | не заменяет мониторинг |

## Вопросы с собеседований

<details><summary>1. Что такое наблюдаемость и чем она отличается от мониторинга?</summary>

Мониторинг отвечает на заранее известные вопросы (графики и алерты по известным метрикам); наблюдаемость — способность по логам, метрикам и трассам разобраться в **незапланированных** проблемах.

</details>

<details><summary>2. Три сигнала наблюдаемости и когда какой использовать?</summary>

Метрики — «что-то не так, насколько» (алерты и тренды), трассы — «где потеряно время/где ошибка в цепочке сервисов», логи — «что именно произошло» (детали). Их связывают общими идентификаторами.

</details>

<details><summary>3. Что такое OpenTelemetry?</summary>

Независимый от поставщика стандарт API, SDK и протокола OTLP для логов, метрик и трасс. В .NET источники — часть платформы (`ActivitySource`, `Meter`), SDK подписывается на них и экспортирует.

</details>

<details><summary>4. Как связаны `Activity` и спан OpenTelemetry?</summary>

Это одно и то же: `Activity` — реализация спана в .NET; `ActivitySource` — источник, `ActivityKind` — вид (Server, Client, Internal...).

</details>

<details><summary>5. Как трасса переходит из сервиса в сервис?</summary>

Через заголовок W3C `traceparent` (`00-<trace-id>-<span-id>-<flags>`): клиентская инструментация добавляет его, серверная — читает и создаёт дочерний спан. Проверено: пять спанов в одной трассе при вызове `/outer` → `/inner`.

</details>

<details><summary>6. Что такое кардинальность метрики и почему она важна?</summary>

Число уникальных комбинаций значений тегов; каждая — отдельный ряд. `user_id` как тег даёт миллионы рядов и ломает бэкенд.

</details>

<details><summary>7. Чем отличаются Counter, UpDownCounter, Histogram и ObservableGauge?</summary>

Counter — монотонный счётчик; UpDownCounter растёт и убывает; Histogram — распределение значений (перцентили); ObservableGauge — текущее значение, читаемое по запросу.

</details>

<details><summary>8. Чем liveness отличается от readiness?</summary>

Liveness — процесс жив (без внешних зависимостей; при провале перезапуск), readiness — готов принимать трафик (проверяет зависимости; при провале убирают из балансировки). Проверено: при падении БД `/health/live` — 200, `/health/ready` — 503.

</details>

<details><summary>9. Что такое сэмплирование трасс и какие бывают виды?</summary>

Выбор, какие трассы сохранять: head (решение в начале, `ParentBased`/по доле) и tail (на коллекторе по итогам, сохраняя ошибки и медленные). Решение должно быть согласованным по сервисам.

</details>

<details><summary>10. Что такое SLI, SLO и бюджет ошибок?</summary>

SLI — измеримый показатель, SLO — цель по нему, бюджет ошибок — допустимая доля сбоев; им управляют темпом релизов.

</details>

<details><summary>11. Вопрос с подвохом: `activity.Tags` пуст, хотя вы вызвали `SetTag("order.id", 42)`. Почему?</summary>

`Tags` содержит только строковые теги; число лежит в `TagObjects` (проверено).

</details>

<details><summary>12. Вопрос с подвохом: спаны есть в коде, но экспортёр ничего не получает. Почему?</summary>

Не подписались на источник (`AddSource("Demo.Shop")`) или сэмплер вернул `None` — тогда `StartActivity` даёт `null` (проверено).

</details>

<details><summary>13. Вопрос с подвохом: проверка здоровья вернула `Degraded`, а балансировщик продолжает слать трафик. Почему?</summary>

По умолчанию `Degraded` отвечает HTTP 200 (проверено); для 503 нужно настроить `ResultStatusCodes`.

</details>
