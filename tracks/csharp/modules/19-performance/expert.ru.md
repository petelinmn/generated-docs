## JIT и ступенчатая компиляция

Код .NET компилируется в IL, а в машинный код его превращает JIT при первом вызове. Чтобы приложение быстро стартовало и при этом хорошо работало на горячих участках, используется **ступенчатая компиляция** (tiered compilation): метод сначала компилируется быстро и без сложных оптимизаций (tier 0), а когда он оказывается «горячим», перекомпилируется оптимизированно (tier 1). Горячие циклы в долго выполняющихся методах заменяются на лету (OSR, on-stack replacement). Динамический PGO (profile-guided optimization) собирает статистику выполнения на ранних ступенях и использует её для оптимизации: девиртуализации вызовов, расположения кода.

Следствия для измерений: первые вызовы метода медленнее установившихся; поэтому бенчмарки прогревают код, а `Stopwatch` вокруг одного вызова ничего не доказывает. Режимы **ReadyToRun** (предкомпилированный код, быстрее старт, затем перекомпиляция горячих методов) и **Native AOT** (полностью предкомпилированный исполняемый файл) убирают часть расходов старта.

> ⚠️ Проверить: конкретные пороги перехода между ступенями и настройки (`TieredCompilation`, `TieredPGO`, `TC_QuickJitForLoops`) зависят от версии runtime; сверьтесь с документацией «Configuring tiered compilation» для .NET 11, прежде чем использовать числа.

## Native AOT

`PublishAot=true` компилирует приложение заранее в машинный код без JIT. Проверено: консольное приложение «hello» опубликовано командой `dotnet publish -c Release` (нужен компонент C++ toolchain для платформы), получен самостоятельный `aot.exe` размером около 900 КБ (923 136 байт) без установленного runtime; `RuntimeFeature.IsDynamicCodeSupported` там `False` (под JIT — `True`, `IsDynamicCodeCompiled` — `True`). Плюсы: быстрый старт, небольшой размер, нет JIT. Ограничения: нет динамической генерации кода (`Reflection.Emit`, часть выражений), рефлексия ограничена обрезкой (trimming), нужны генераторы исходников (JSON, регулярные выражения, привязка конфигурации), и публикация — под конкретную платформу. Подходит для CLI, serverless и контейнеров с быстрым стартом; неудобно для приложений, активно использующих рефлексию ([20 · Рефлексия и генераторы кода](../20-reflection-and-source-generators/overview.ru.md)).

## SIMD и векторизация

Современные процессоры обрабатывают несколько значений одной инструкцией (SIMD). В .NET: `Vector<T>` (размер зависит от машины), `Vector128/256/512<T>`, и векторизованные методы BCL (`Span.IndexOf`, `SequenceEqual`, `Sum` у некоторых типов, `SearchValues`). Проверено: на тестовой машине `Vector.IsHardwareAccelerated == True`, `Vector<int>.Count == 8` (256 бит); сумма 1000 чисел через `Vector<int>` совпала с `Sum()` (`499500`):

```csharp
static int SumVec(int[] a)
{
    var acc = Vector<int>.Zero; int i = 0;
    for (; i <= a.Length - Vector<int>.Count; i += Vector<int>.Count) acc += new Vector<int>(a, i);
    int s = Vector.Sum(acc);
    for (; i < a.Length; i++) s += a[i];            // the tail that did not fit a whole vector
    return s;
}
```

Писать SIMD вручную стоит только для самых горячих ядер после замера; чаще достаточно готовых методов BCL.

## Режимы GC

| Режим | Особенность |
|---|---|
| Workstation, concurrent (по умолчанию в проверенной среде: `ServerGC=False`, `LatencyMode=Interactive`) | малые паузы для интерактивных приложений |
| Server | отдельные кучи и потоки GC на ядро; выше пропускная способность, больше памяти |
| Non-concurrent | без фонового GC; меньше накладных расходов |
| `GCSettings.LatencyMode` / `GC.TryStartNoGCRegion` | временные ограничения на сборки в критических участках |

Режим задают в `runtimeconfig.json` (`System.GC.Server`, `System.GC.Concurrent`) или переменными окружения. Подробно о поколениях и режимах — в [12 · Память и GC](../12-memory-and-gc/expert.ru.md).

## Ловушки микробенчмарков

- **Устранение мёртвого кода.** Если результат вычисления не используется, JIT может выбросить его: возвращайте значение из бенчмарка.
- **Свёртывание констант.** Константный вход позволяет вычислить результат на этапе компиляции: данные берут из полей/`GlobalSetup`.
- **Прогрев и ступени JIT.** Измеряйте после стабилизации; BenchmarkDotNet это делает.
- **Шум машины.** Фоновые процессы, режимы питания, термоограничения: закройте лишнее, сравнивайте отношения.
- **Нерепрезентативные данные.** Размер и форма входа влияют на результат (`[Params]`).
- **Разброс.** `ShortRun` даёт большую погрешность (в проверенных запусках `Error` составлял десятки процентов): для выводов нужен полный режим.
- **Измерение не того.** Микробенчмарк не показывает влияния на GC всего приложения — смотрите выделения.

## Подвохи

**1. Оптимизация без замера.** Самый частый источник усложнения кода без выгоды.

**2. Debug и Release.** Debug может быть на порядок медленнее; результаты BenchmarkDotNet в Debug запрещены.

**3. Абсолютные числа с чужой машины.** Сравнивайте отношения и выделения.

**4. LINQ «всегда медленный».** Выделения LINQ на 1000 элементов (48 Б) невелики; в большинстве мест он уместен. Цикл быстрее в ~3 раза, но важен ли он в вашем горячем пути — решает профиль.

**5. `static`-лямбда против лямбды с захватом.** 0 против 80 байт на вызов (проверено): в горячем коде избегайте захвата.

**6. Закрытая коллекция как `IEnumerable<T>`.** `foreach` по `List<int>` через интерфейс выделяет 40 байт (боксированный перечислитель), через тип `List<int>` — 0 (проверено).

**7. `params object[]`.** Каждый вызов с аргументами — выделение массива и упаковка (120 байт на три числа); `params ReadOnlySpan<T>` — 0 (проверено).

**8. Пул без возврата.** `ArrayPool` быстр, пока вы возвращаете буферы; забытый `Return` превращает его в обычное выделение.

## Компромиссы и альтернативы

| Подход | Плюсы | Минусы |
|---|---|---|
| Читаемый код с LINQ | проще поддерживать | выделения в горячем пути |
| Ручные циклы, пулы, `Span` | меньше выделений | сложнее и хрупче |
| Native AOT | старт и размер | ограничения рефлексии и динамического кода |
| ReadyToRun | быстрее старт | больше размер сборок |
| Server GC | пропускная способность | больше памяти |
| Кэширование результатов | убирает работу | инвалидация и память |

## Вопросы с собеседований

<details><summary>1. Как вы подходите к оптимизации производительности?</summary>

Измеряю: профилировщик показывает узкое место, бенчмарк сравнивает варианты, метрики (выделения, сборки GC) показывают побочные эффекты. Затем правлю одно место и измеряю снова. Без измерения оптимизировать нельзя.

</details>

<details><summary>2. Почему нельзя измерять `Stopwatch` одним запуском?</summary>

Первый вызов включает JIT-компиляцию и прогрев, разброс велик, оптимизации JIT меняются по ступеням. Нужны прогрев, много итераций и статистика — BenchmarkDotNet.

</details>

<details><summary>3. Что такое ступенчатая компиляция?</summary>

Метод сначала компилируется быстро (tier 0), горячий — перекомпилируется оптимизированно (tier 1); циклы заменяются на лету (OSR); динамический PGO использует профиль выполнения.

</details>

<details><summary>4. Что такое давление на GC и как его снизить?</summary>

Большое число выделений вызывает частые сборки (проверено: 22 сборки gen0 на 200 тыс. выделений по 1 КБ). Снижают: пулы, `Span`/`stackalloc`, структуры, отказ от упаковки и лишних строк/LINQ в горячем пути.

</details>

<details><summary>5. Когда `StringBuilder`, а когда `+`?</summary>

`+` для нескольких фиксированных кусков (компилятор оптимизирует); в цикле — `StringBuilder` или `string.Concat/Join` (проверено: 50 склеек — 7968 против 1176 и 304 байт).

</details>

<details><summary>6. Что такое Native AOT и каковы его ограничения?</summary>

Предварительная компиляция в машинный код без JIT: быстрый старт и малый размер, без установленного runtime. Ограничения: нет динамической генерации кода, рефлексия и обрезка требуют генераторов и аннотаций.

</details>

<details><summary>7. Для чего `ArrayPool<T>` и какие у него риски?</summary>

Переиспользование больших массивов вместо выделений. Риски: не вернули (`Return`), использовали после возврата, не обнулён, длина больше запрошенной.

</details>

<details><summary>8. Что делает `[MemoryDiagnoser]`?</summary>

Добавляет в отчёт число сборок по поколениям и выделенную память на операцию — самые стабильные числа бенчмарка.

</details>

<details><summary>9. Что даёт SIMD?</summary>

Обработку нескольких значений одной инструкцией: `Vector<T>`, `Vector128/256/512`, векторизованные методы BCL. Выигрыш на длинных данных; вручную — только для самых горячих ядер.

</details>

<details><summary>10. Вопрос с подвохом: быстрее ли цикл по `Span`, чем по массиву?</summary>

Нет: в проверенном замере цикл по `int[]` и по `Span<int>` дали одинаковое время (254 нс) — JIT убирает проверки границ в обоих случаях. Выигрыш `Span` — в отсутствии копий.

</details>

<details><summary>11. Вопрос с подвохом: бенчмарк показал огромное ускорение, но в приложении ничего не изменилось. Почему?</summary>

Возможно, JIT выбросил неиспользуемый результат или константы свернулись; либо участок не горячий в реальной нагрузке. Нужны возвращаемое значение, реалистичные входные данные и профиль приложения.

</details>

<details><summary>12. Вопрос с подвохом: почему BenchmarkDotNet в Debug отказывается работать?</summary>

Debug-сборка не оптимизирована, результаты бессмысленны; программа сообщает «built without optimization enabled» (проверено).

</details>
