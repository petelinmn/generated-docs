# Коллекции и обобщения: экспертная теория

🌐 **Русский** · [English](expert.en.md)

**Уровни:** [обзор](overview.ru.md) · [1. Базовая](basics.ru.md) · [2. Продвинутая](advanced.ru.md) · **3. Экспертная**

## Под капотом

### List<T>

Внутри `List<T>` три закрытых поля (проверено через рефлексию): массив `_items`, счётчик `_size` и номер версии `_version`. `Count` — это `_size`, `Capacity` — длина `_items`. При добавлении в заполненный список выделяется новый массив вдвое больше (`0 → 4 → 8 → 16 → 32`) и элементы копируются. Каждое изменение увеличивает `_version`; перечислитель `List<T>.Enumerator` — структура, запоминает версию при создании и сравнивает при каждом `MoveNext`: поэтому изменение во время `foreach` даёт `InvalidOperationException`. Структурный перечислитель не создаёт объекта в куче, если `foreach` идёт по переменной типа `List<T>`, а если привести её к `IEnumerable<T>`, перечислитель упаковывается ([03 · Управляющие конструкции и методы](../03-control-flow-and-methods/expert.ru.md)).

### Dictionary<TKey, TValue>

Поля `Dictionary` (проверено): `_buckets`, `_entries`, `_fastModMultiplier`, `_count`, `_freeList`, `_freeCount`, `_version`, `_comparer`. Это **хеш-таблица с цепочками на массивах**:

1. Хеш ключа (`comparer.GetHashCode(key)`) сводится к номеру корзины в `_buckets`.
2. В корзине хранится индекс первой записи в массиве `_entries`; каждая запись содержит ключ, значение, хеш и индекс **следующей записи** в той же корзине. Так обрабатываются коллизии: по цепочке сравниваются хеш и ключ (`Equals`).
3. Удалённая запись попадает в список свободных (`_freeList`), и следующая вставка занимает её место. Поэтому после `Remove(1)` и добавления ключа `9` порядок перечисления был `3,9,2`, а не `3,2,9` (проверено).
4. Число корзин — **простое число**: после добавления 1 элемента корзин 3, после 20 — 37, `EnsureCapacity(100)` вернул 107 (проверено). При заполнении таблица перестраивается в большую.

Из этого следует требование к ключам: `GetHashCode` должен быть быстрым и равномерным, а равные ключи — давать равные хеши. Для `string` runtime использует **рандомизированный** хеш: значение `"abc".GetHashCode()` различалось между двумя запусками (1199515494 и 373536423), что защищает от атак, подбирающих коллизии. Поэтому нельзя сохранять хеш строки между запусками.

`HashSet<T>` устроен так же (те же поля без значений), `SortedDictionary` и `SortedSet` — сбалансированное дерево, `Stack<T>` — массив `_array`, `_size`, `_version`.

### Выражения коллекций

Компилятор выбирает способ создания по целевому типу. Проверено по типам во время выполнения: для `ICollection<int>` создаётся `List<int>`, а для `IEnumerable<int>` и `IReadOnlyList<int>` — специальные компилятор-генерируемые типы только для чтения (`<>z__ReadOnlyArray`1`, `<>z__ReadOnlySingleElementList`1`). Для `ReadOnlySpan<int>` данные не выделяются в куче.

### Обобщения в runtime

В отличие от Java, .NET **овеществляет** (reifies) обобщения: информация о параметрах типа сохраняется во время выполнения.

- `typeof(List<>)` — открытый обобщённый тип, `typeof(List<int>)` — закрытый конструированный; `typeof(Dictionary<,>).GetGenericArguments().Length` — 2 (проверено).
- Каждый закрытый тип — **отдельный тип** со своими статическими полями: `Counter<int>.Next()` дал `1, 2`, а `Counter<string>.Next()` начал с `1` заново (проверено).
- Для значимых типов JIT создаёт отдельную специализацию кода, поэтому `List<int>` хранит значения прямо в массиве: добавление 1000 `int` не выделило ни байта (измерено в [12 · Память и GC](../12-memory-and-gc/advanced.ru.md#измерение-выделений-памяти)), в отличие от `ArrayList` (24 000 байт).
- Вызов метода интерфейса через параметр типа с ограничением не упаковывает структуру (0 байт против 24 для интерфейсного параметра — [05 · Интерфейсы, структуры, записи](../05-interfaces-structs-records/expert.ru.md#упаковка-и-constrained-вызовы)).
- Без ограничений у `T` доступны только члены `object`: операторы или методы типа вызвать нельзя; статические абстрактные члены интерфейсов позволяют `T.Add(a, b)` ([05](../05-interfaces-structs-records/advanced.ru.md#статические-члены-интерфейсов)).

## Справочник

### Сложность операций

| Коллекция | Доступ по индексу/ключу | Поиск значения | Вставка | Удаление |
|---|---|---|---|---|
| `T[]` | `O(1)` | `O(n)` | — (размер фиксирован) | — |
| `List<T>` | `O(1)` | `O(n)` | `O(1)` амортиз. в конец, `O(n)` в середину | `O(n)` |
| `Dictionary<K,V>` | `O(1)` в среднем | `O(n)` | `O(1)` в среднем | `O(1)` в среднем |
| `HashSet<T>` | — | `O(1)` в среднем | `O(1)` в среднем | `O(1)` в среднем |
| `SortedDictionary<K,V>`, `SortedSet<T>` | `O(log n)` | `O(log n)` | `O(log n)` | `O(log n)` |
| `Queue<T>`, `Stack<T>` | — | `O(n)` | `O(1)` | `O(1)` |
| `PriorityQueue<E,P>` | — | — | `O(log n)` | `O(log n)` |
| `LinkedList<T>` | — | `O(n)` | `O(1)` при наличии узла | `O(1)` при наличии узла |

### Интерфейсы и их члены

| Интерфейс | Ключевые члены | Реализуют |
|---|---|---|
| `IEnumerable<T>` | `GetEnumerator()` | все коллекции, `string` (`IEnumerable<char>`) |
| `ICollection<T>` | `Count`, `Add`, `Remove`, `Contains`, `Clear`, `CopyTo` | `List`, `HashSet`, `Dictionary` |
| `IList<T>` | индексатор, `Insert`, `RemoveAt`, `IndexOf` | `List`, массивы |
| `IReadOnlyCollection<T>`, `IReadOnlyList<T>`, `IReadOnlyDictionary<K,V>` | `Count`, индексатор | почти все |
| `ISet<T>`, `IReadOnlySet<T>` | `UnionWith`, `IntersectWith`, `IsSubsetOf`, … | `HashSet`, `SortedSet` |
| `IComparer<T>`, `IEqualityComparer<T>` | `Compare`, `Equals`/`GetHashCode` | компараторы для `Sort` и словарей |

### Вариантность типов

| Тип | Вариантность |
|---|---|
| `IEnumerable<out T>`, `IEnumerator<out T>`, `IReadOnlyList<out T>`, `IReadOnlyCollection<out T>` | ковариантны |
| `Func<…, out TResult>` | ковариантен по результату, контравариантен по параметрам (`in T`) |
| `Action<in T>`, `IComparer<in T>`, `IEqualityComparer<in T>`, `IComparable<in T>` | контравариантны |
| `List<T>`, `IList<T>`, `ICollection<T>`, `Dictionary<K,V>`, `HashSet<T>` | инвариантны |
| массивы ссылочных типов | ковариантны с проверкой при записи (`ArrayTypeMismatchException`) |

Правила: `out` — параметр только в позициях результата; `in` — только в позициях аргументов; вариантность работает только между **ссылочными** типами и только на интерфейсах и делегатах.

### Классы и интерфейсы для сравнения

| Нужно | Реализовать |
|---|---|
| естественный порядок | `IComparable<T>` |
| порядок «со стороны» | `IComparer<T>` / делегат `Comparison<T>` |
| равенство в коллекциях | `IEquatable<T>` + `GetHashCode` |
| нестандартное равенство для одного словаря | `IEqualityComparer<T>` в конструкторе |
| строки без учёта регистра | `StringComparer.OrdinalIgnoreCase` |

## Подвохи

Каждый подвох проверен запуском.

### Ёмкость растёт скачками

Список из 20 элементов имел ёмкость 32, а не 20: удвоение даёт запас. После `TrimExcess` у списка из 3 элементов ёмкость стала 3. Если создать `new List<int>(100)`, ёмкость сразу 100 — без повторных выделений.

### Изменение во время обхода — не всегда ошибка

`List.Add`, `List.Remove`, `Dictionary.Add` во время `foreach` бросают `InvalidOperationException`. А `Dictionary.Remove` и присваивание **существующему** ключу — нет (на .NET 11). Не стоит строить на этом код: для `List` и `HashSet` правила другие.

### Порядок перечисления Dictionary

Ключи шли в порядке вставки (`3,1,2`), пока ничего не удаляли. После `Remove(1)` и вставки `9`: `3,9,2`. Порядок — побочный эффект реализации, а не гарантия.

### Ковариантность массивов

`object[] objs = new string[]{"a"}; objs[0] = 1;` → `ArrayTypeMismatchException` во время выполнения, а не ошибка компиляции.

### List<string> не является List<object>

`new List<string>() is List<object>` → `False` (инвариантность). Зато `IEnumerable<object> eo = new List<string>{ "a" };` работает.

### ReadOnlyCollection — представление, а не копия

После `src.Add(3)` обёртка `new ReadOnlyCollection<int>(src)` показывает `Count == 3`. Настоящая копия — `ImmutableList` (`ToImmutableList()` снимок: после добавления в исходный список в неизменяемом остались прежние 3 элемента).

### IReadOnlyList можно привести обратно

`iro as List<int>` вернул не `null`: интерфейс только скрывает методы, но не защищает. Для настоящей защиты — `AsReadOnly()` или `ImmutableArray`.

### Результат BinarySearch

Для `{1,3,5}`: найденный `3` → `1`; отсутствующий `4` → `-3` — это `~2`, то есть позиция вставки `2` в побитовом отрицании. Проверка `result >= 0` — «найден».

### Статические поля обобщённого типа

У каждого закрытого типа своё статическое поле: `Counter<int>` и `Counter<string>` считают независимо (`1, 2` и `1`).

### Хеш строки меняется между запусками

Два запуска дали `1199515494` и `373536423` для `"abc"`. Нельзя записывать `GetHashCode` строки в файл или базу.

### null-ключ

`dict[null!] = 1` → `ArgumentNullException`. У `HashSet<T>` `null` допустим, у `Dictionary` как ключ — нет.

### Устойчивость сортировки

`OrderBy` сохранил порядок равных ключей (`c,b,a` для `("b",1),("a",1),("c",0)`). `List.Sort` и `Array.Sort` этого не гарантируют.

## Компромиссы и альтернативы

| Задача | Вариант | Цена |
|---|---|---|
| Быстрый поиск по ключу | `Dictionary` | память на таблицу; порядок не гарантирован |
| Отсортированный обход | `SortedDictionary` | `O(log n)` на операцию |
| | `Dictionary` + сортировка при необходимости | сортировка при каждом обходе |
| Справочник, строится один раз | `FrozenDictionary` | долгое создание, быстрое чтение |
| Неизменяемость, потокобезопасность | `Immutable*` | каждое «изменение» создаёт новую коллекцию |
| Только чтение в API | `IReadOnlyList<T>` | не защищает от приведения обратно |
| Очередь для потоков | `ConcurrentQueue`, `Channel<T>` | см. [18 · Многопоточность](../18-concurrency/advanced.ru.md) |
| Минимум выделений | `Span<T>`, `ArrayPool<T>`, `CollectionsMarshal` | сложнее код и время жизни |

## Вопросы с собеседований

**1. Как устроен `List<T>`? Как растёт ёмкость?**

<details><summary>Ответ</summary>

Массив `_items`, счётчик `_size` и версия `_version`. При переполнении выделяется массив вдвое больше (`0 → 4 → 8 → 16 → 32`, проверено) и элементы копируются, поэтому `Add` — амортизированно `O(1)`. Вставка в середину — `O(n)` (сдвиг). Известный размер лучше задать в конструкторе.

</details>

**2. Как устроен `Dictionary<K,V>`?**

<details><summary>Ответ</summary>

Хеш-таблица с цепочками на массивах: `_buckets` (индекс первой записи) и `_entries` (ключ, значение, хеш, индекс следующей записи в цепочке). Хеш ключа даёт корзину, по цепочке сравниваются хеш и `Equals`. Число корзин — простое (3, 37, 107 в проверках). Удалённые записи идут в список свободных и переиспользуются, поэтому порядок перечисления не гарантирован.

</details>

**3. Какая сложность операций у `Dictionary`? Когда она деградирует?**

<details><summary>Ответ</summary>

Поиск, вставка и удаление — `O(1)` в среднем. Деградирует до `O(n)`, если `GetHashCode` даёт много коллизий (плохой хеш, например, константа). Хеш строк рандомизирован runtime, что защищает от намеренного подбора коллизий.

</details>

**4. Почему нельзя изменять коллекцию в `foreach`? Что делать?**

<details><summary>Ответ</summary>

Перечислитель запоминает версию коллекции и сверяет при каждом `MoveNext`; изменение даёт `InvalidOperationException` («Collection was modified…»). Решения: `RemoveAll`, цикл `for` с конца, обход копии (`ToList()`), сбор изменений и применение после цикла. `Dictionary.Remove` и запись по существующему ключу в .NET 11 допустимы, но на это опираться не стоит.

</details>

**5. Чем `List<T>` отличается от массива? Когда массив лучше?**

<details><summary>Ответ</summary>

Массив имеет фиксированный размер, доступ быстрее (нет проверки версии и лишнего уровня), поддерживает многомерность и ковариантность. `List<T>` растёт и удобнее. Массив — когда размер известен и важна скорость (в том числе `Span<T>` над ним).

</details>

**6. Что такое ковариантность и контравариантность? Приведи примеры.**

<details><summary>Ответ</summary>

Ковариантность (`out T`) — `IEnumerable<string>` можно использовать как `IEnumerable<object>` (только чтение). Контравариантность (`in T`) — `Action<object>` можно присвоить `Action<string>` (только передача). `List<T>` инвариантен: `List<string>` — не `List<object>`, иначе в него можно было бы положить `int`. Работает только для ссылочных типов, интерфейсов и делегатов.

</details>

**7. Подвох: почему массивы ковариантны и чем это опасно?**

<details><summary>Ответ</summary>

Историческое решение .NET 1.0 (до появления обобщений). `object[] a = new string[1]; a[0] = 1;` компилируется, но бросает `ArrayTypeMismatchException` во время выполнения: каждая запись в массив ссылочных типов проверяет тип (проверено).

</details>

**8. Как устроены обобщения в .NET? Чем они отличаются от Java?**

<details><summary>Ответ</summary>

Овеществлены: параметры типа сохраняются во время выполнения, `typeof(List<int>)` и `typeof(List<string>)` — разные типы со своими статическими полями (проверено), для значимых типов JIT создаёт отдельный код без упаковки. В Java обобщения стираются при компиляции (type erasure) и значения примитивов упаковываются.

</details>

**9. Какие ограничения параметров типа есть и зачем они нужны?**

<details><summary>Ответ</summary>

`class`, `struct`, `new()`, базовый класс, интерфейс, `notnull`, `unmanaged`, `allows ref struct`, другой параметр типа. Ограничение даёт доступ к членам: без `where T : IComparable<T>` нельзя вызвать `CompareTo`, без `new()` — `new T()`, без `unmanaged` — `Unsafe.SizeOf<T>()`.

</details>

**10. Чем `IEnumerable<T>`, `ICollection<T>`, `IList<T>`, `IReadOnlyList<T>` отличаются? Что принимать и что возвращать?**

<details><summary>Ответ</summary>

`IEnumerable<T>` — только обход; `IReadOnlyList<T>` — + `Count` и индекс без изменения; `ICollection<T>` — + изменение и `Count`; `IList<T>` — + индекс и `Insert`. Принимать — самый узкий интерфейс, которого хватает; возвращать — `IReadOnlyList<T>` или конкретный тип (но не изменяемую внутреннюю коллекцию).

</details>

**11. Чем `ReadOnlyCollection<T>`, `IReadOnlyList<T>` и `ImmutableList<T>` отличаются?**

<details><summary>Ответ</summary>

`IReadOnlyList<T>` — только интерфейс: объект остаётся изменяемым и приводится обратно к `List<T>`. `ReadOnlyCollection<T>` — обёртка-представление: сама не изменяется, но показывает изменения исходного списка (после `src.Add(3)` `Count == 3`). `ImmutableList<T>` — настоящая неизменяемость: операции возвращают новую коллекцию.

</details>

**12. Когда использовать `HashSet<T>`, а когда `List<T>`?**

<details><summary>Ответ</summary>

`HashSet<T>` — для уникальности и быстрой проверки «есть ли элемент» (`O(1)` в среднем), порядок не важен. `List<T>` — когда нужен порядок и индексы, дубликаты допустимы. `Contains` в списке — `O(n)`, поэтому в цикле он превращает алгоритм в квадратичный.

</details>

**13. В чём разница между `OrderBy` и `List.Sort`?**

<details><summary>Ответ</summary>

`OrderBy` (LINQ) возвращает новую последовательность и **устойчив** (равные ключи сохраняют порядок). `List.Sort` сортирует на месте интроспективной сортировкой и **не гарантирует устойчивость**. Проверено на `("b",1),("a",1),("c",0)`: `OrderBy` дал `c,b,a`.

</details>

**14. Что вернёт `BinarySearch`, если элемента нет?**

<details><summary>Ответ</summary>

Отрицательное число — побитовое отрицание позиции, в которую элемент нужно вставить (`~index`). Для `{1,3,5}` и `4` результат `-3` = `~2`. Список должен быть отсортирован, иначе результат непредсказуем.

</details>

**15. Подвох: почему после `Remove` и `Add` порядок ключей в `Dictionary` изменился?**

<details><summary>Ответ</summary>

Освободившаяся запись попадает в список свободных (`_freeList`), и следующая вставка занимает её место в массиве `_entries`. Порядок перечисления — порядок записей в массиве, поэтому `3,1,2` после удаления `1` и добавления `9` стал `3,9,2`. Порядок не гарантирован документацией.

</details>

**16. Что делает `where T : unmanaged`?**

<details><summary>Ответ</summary>

Разрешает только значимые типы, не содержащие ссылок (числа, `bool`, `char`, `enum`, структуры из таких полей). Позволяет брать размер (`Unsafe.SizeOf<T>()` — 4 для `int`, 8 для `long`) и указатель на значение, что нужно для низкоуровневого и взаимодействующего кода.

</details>

**17. Как работают выражения коллекций? Какой тип создаётся?**

<details><summary>Ответ</summary>

Компилятор выбирает способ по целевому типу: массив, `List<T>`, `Span<T>`/`ReadOnlySpan<T>` без выделения в куче, интерфейсы (для `ICollection<T>` — `List<T>`, для `IEnumerable<T>`/`IReadOnlyList<T>` — генерируемый компилятором тип только для чтения). `..` вставляет элементы другой последовательности.

</details>

| Нужно | Решение |
|---|---|
| Список с известным размером | `new List<T>(n)` |
| Удалить по условию | `RemoveAll(predicate)` |
| Безопасно прочитать из словаря | `TryGetValue`, `GetValueOrDefault` |
| Обновить значение с одним поиском | `CollectionsMarshal.GetValueRefOrAddDefault` |
| Уникальность, `Contains` | `HashSet<T>` |
| Всегда отсортировано | `SortedSet<T>`, `SortedDictionary<K,V>` |
| Сначала главное | `PriorityQueue<E,P>` |
| Неизменяемый справочник | `FrozenDictionary` |
| Копия массива | `[..a]`, `Clone()` |
| Ковариантный параметр | `IEnumerable<T>`, `IReadOnlyList<T>` |
| Ограничение параметра | `where T : …` |
| Устойчивая сортировка | `OrderBy` |
