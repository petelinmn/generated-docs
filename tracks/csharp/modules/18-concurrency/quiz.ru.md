# Квиз: Многопоточность и синхронизация

## 1. 🟢 Четыре потока по миллиону раз выполняют `_value++` над общим полем без синхронизации. Что будет?

- A) Ровно 4 000 000
- B) Исключение `InvalidOperationException`
- C) Число не больше 4 000 000, разное от запуска к запуску
- D) Ровно 1 000 000: потоки перезаписывают друг друга целиком

<details><summary>Ответ</summary>

**C.** `_value++` — это чтение, сложение и запись. Два потока могут прочитать одно значение, и одно увеличение потеряется. В реальном запуске получилось 1 966 527. Исключения нет: гонка молча портит данные.
→ [Базовая теория](basics.ru.md)

</details>

## 2. 🟢 Какой объект лучше всего использовать в `lock`?

- A) `this`
- B) строковый литерал `"orders"`
- C) `typeof(OrderService)`
- D) `private readonly Lock _gate = new();`

<details><summary>Ответ</summary>

**D.** Приватный объект, который существует только для блокировки. `this` и `Type` может заблокировать чужой код, а строковые литералы интернированы и общие для всей программы. С .NET 9 для этого есть тип `System.Threading.Lock`.
→ [Базовая теория](basics.ru.md)

</details>

## 3. 🟢 Что вернёт `Interlocked.Exchange(ref x, 7)`, если `x == 5`?

- A) `7`
- B) `5`
- C) `true`
- D) `12`

<details><summary>Ответ</summary>

**B.** `Exchange` записывает новое значение и возвращает **прежнее**. После вызова `x == 7`. `CompareExchange` тоже возвращает прежнее значение.
→ [Базовая теория](basics.ru.md)

</details>

## 4. 🟢 Какие потоки не дают процессу завершиться, пока они работают?

- A) Все потоки без исключения
- B) Потоки, созданные через `new Thread` с настройками по умолчанию
- C) Потоки пула, на которых выполняется `Task.Run`
- D) Никакие: процесс завершается вместе с `Main`

<details><summary>Ответ</summary>

**B.** `new Thread` по умолчанию foreground (`IsBackground = False`), и процесс ждёт его завершения. Потоки пула — background и завершаются вместе с процессом.
→ [Базовая теория](basics.ru.md)

</details>

## 5. 🟢 Выбери все верные утверждения

- [ ] A) `Interlocked.Increment` атомарен и не требует `lock`
- [ ] B) Если два поля должны меняться согласованно, достаточно `Interlocked` для каждого
- [ ] C) `lock` освобождается даже при исключении внутри блока
- [ ] D) Обычный `Dictionary` безопасен для одновременной записи из нескольких потоков

<details><summary>Ответ</summary>

**A, C.** Отдельные атомарные операции над двумя полями не делают атомарной их пару — между ними другой поток увидит промежуточное состояние (B неверно). `lock` разворачивается в `try/finally` (C верно). `Dictionary` не рассчитан на одновременную запись (D неверно): нужен `ConcurrentDictionary` или `lock`.
→ [Базовая теория](basics.ru.md)

</details>

## 6. 🟡 Что произойдёт с этим кодом?

```csharp
object g = new();
lock (g) { await Task.Delay(1); }
```

- A) Работает, но медленно
- B) Ошибка компиляции CS1996
- C) `SynchronizationLockException` во время выполнения
- D) Взаимоблокировка

<details><summary>Ответ</summary>

**B.** `await` внутри `lock` запрещён: после `await` код может продолжиться в другом потоке, а `Monitor` привязан к потоку-владельцу. Решение — `SemaphoreSlim(1, 1)` с `await WaitAsync()` и `Release()` в `finally`.
→ [Продвинутая теория](advanced.ru.md)

</details>

## 7. 🟡 12 асинхронных задач запускаются через `SemaphoreSlim(3, 3)`: каждая делает `await WaitAsync()`, работает 20 мс и вызывает `Release()`. Сколько задач выполняется одновременно?

- A) 12
- B) Не больше 3
- C) Ровно 1
- D) Зависит от числа ядер процессора

<details><summary>Ответ</summary>

**B.** Семафор со счётчиком 3 пропускает не больше трёх участников. В реальном запуске пик был ровно 3. Ожидание в `WaitAsync` не блокирует потоки, поэтому число ядер здесь не важно.
→ [Продвинутая теория](advanced.ru.md)

</details>

## 8. 🟡 Поток вызвал `rw.EnterReadLock()`, затем, не отпуская его, `rw.EnterWriteLock()` у `ReaderWriterLockSlim` с настройками по умолчанию. Что будет?

- A) Блокировка повысится до записи
- B) Поток зависнет навсегда
- C) `LockRecursionException`
- D) Запись выполнится без блокировки

<details><summary>Ответ</summary>

**C.** С политикой по умолчанию `NoRecursion` это исключение: «Write lock may not be acquired with read lock held». Для сценария «прочитать и, возможно, записать» есть `EnterUpgradeableReadLock`.
→ [Продвинутая теория](advanced.ru.md)

</details>

## 9. 🟡 8 потоков одновременно вызывают `dict.GetOrAdd("key", factory)` у пустого `ConcurrentDictionary`. Сколько раз выполнится `factory`?

- A) Ровно 1 — `ConcurrentDictionary` потокобезопасен
- B) От 1 до 8
- C) Ровно 8
- D) 0 — значение создаётся лениво при чтении

<details><summary>Ответ</summary>

**B.** Фабрика выполняется вне внутренней блокировки словаря. Когда все 8 потоков одновременно оказались внутри фабрики, она выполнилась 8 раз, а в словарь попало одно значение. Чтобы фабрика выполнилась один раз, значение оборачивают в `Lazy<T>`.
→ [Продвинутая теория](advanced.ru.md)

</details>

## 10. 🟡 Найди ошибку

```csharp
void Transfer(Account from, Account to, decimal amount)
{
    lock (from.Gate)
    {
        lock (to.Gate)
        {
            from.Balance -= amount;
            to.Balance += amount;
        }
    }
}
```

<details><summary>Ответ</summary>

Встречные переводы `Transfer(a, b)` и `Transfer(b, a)` захватывают замки в противоположном порядке: первый держит `a` и ждёт `b`, второй держит `b` и ждёт `a`. Это взаимоблокировка. Исправление — единый порядок захвата, например по `Id`: сначала замок счёта с меньшим `Id`, потом с большим.
→ [Продвинутая теория](advanced.ru.md)

</details>

## 11. 🔴 Почему этот код бросает `SynchronizationLockException`?

```csharp
private readonly SpinLock _spin = new(enableThreadOwnerTracking: true);

public void EnterAndExit()
{
    bool taken = false;
    _spin.Enter(ref taken);
    _spin.Exit();
}
```

- A) `SpinLock` нельзя использовать в методах экземпляра
- B) `SpinLock` — структура; для `readonly`-поля `Enter` и `Exit` работают с разными защитными копиями
- C) Отслеживание владельца запрещает вызывать `Exit` сразу после `Enter`
- D) `Enter` не захватил блокировку, потому что `taken` был `false`

<details><summary>Ответ</summary>

**B.** Для вызова метода у `readonly`-поля структуры компилятор передаёт копию. `Enter` блокирует одну копию, а `Exit` вызывается на другой — незаблокированной. Документация прямо запрещает хранить `SpinLock` в `readonly`-полях.
→ [Экспертная теория](expert.ru.md)

</details>

## 12. 🔴 Выбери все верные утверждения о модели памяти

- [ ] A) `volatile int x; x++` атомарно
- [ ] B) Поле `volatile long` не компилируется
- [ ] C) Методы `Interlocked` являются полными барьерами памяти
- [ ] D) Обычные чтения и записи могут переупорядочиваться, если это не меняет поведение в одном потоке

<details><summary>Ответ</summary>

**B, C, D.** `volatile` даёт порядок (acquire/release), но не атомарность составных операций (A неверно). `volatile long` и `volatile double` — ошибка CS0677. `Interlocked` — full fence по модели памяти .NET. Переупорядочивание обычных операций разрешено, пока сохраняется согласованность в одном потоке.
→ [Экспертная теория](expert.ru.md)

</details>

## 13. 🔴 Открытый вопрос

Сервис хранит идентификатор запроса в `ThreadLocal<string>`, а обработчик запроса — асинхронный. В логах иногда пустой или чужой идентификатор. Почему, и как исправить?

<details><summary>Ключевые пункты ответа</summary>

- `ThreadLocal` привязан к потоку ОС, а после `await` код может продолжиться на другом потоке пула — там своё значение или пустое.
- Поток пула мог перед этим обслуживать другой запрос — отсюда «чужой» идентификатор.
- `AsyncLocal<T>` хранит значение в контексте выполнения, который переходит в продолжения после `await` и в новые потоки: в проверенном примере новый поток видит `("request-42", null)`.
- Исправление — `AsyncLocal<string>`.

</details>
