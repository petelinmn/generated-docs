# Квиз: Память и GC

🌐 **Русский** · [English](quiz.en.md)

> Сначала ответь сам, потом раскрывай ответ. Отметка показывает, из какого уровня вопрос: 🟢 [базовая теория](basics.ru.md) · 🟡 [продвинутая](advanced.ru.md) · 🔴 [экспертная](expert.ru.md).

## 1. 🟢 Когда объект может быть собран сборщиком мусора?

- A) когда счётчик ссылок на него станет равен нулю
- B) когда он недостижим из корней: стеков потоков, статических полей, GC-дескрипторов
- C) сразу после выхода из метода, в котором он создан
- D) только после присваивания `null` всем переменным, которые на него ссылались

<details><summary>Ответ</summary>

**B.** GC .NET не считает ссылки, а обходит граф от корней: всё недостижимое — мусор. A описывает подсчёт ссылок (так работает CPython). C неверно: объект, возвращённый из метода или сохранённый в поле, продолжает жить. D неверно: присваивание `null` не обязательно и не гарантирует сборку — объект собирается, когда до него нельзя добраться, и только при ближайшей сборке его поколения.
→ [Базовая теория](basics.ru.md#как-gc-решает-что-объект-больше-не-нужен)

</details>

## 2. 🟢 Объекты `a` и `b` ссылаются друг на друга, и больше на них никто не ссылается. Что сделает GC?

- A) ничего: у каждого есть ссылка, поэтому они живы
- B) соберёт оба
- C) соберёт один из них
- D) бросит исключение о циклической ссылке

<details><summary>Ответ</summary>

**B.** GC ищет достижимые из корней объекты, а цикл недостижим. Проверено: после `GC.Collect()` слабая ссылка на объект из цикла стала недействительной. Утечку через циклы даёт подсчёт ссылок без отдельного сборщика циклов, но не GC .NET.
→ [Базовая теория](basics.ru.md#как-gc-решает-что-объект-больше-не-нужен)

</details>

## 3. 🟢 Что выведет код?

```csharp
var survivor = new object();
var generations = new List<int> { GC.GetGeneration(survivor) };
for (int i = 0; i < 3; i++)
{
    GC.Collect();
    generations.Add(GC.GetGeneration(survivor));
}
Console.WriteLine(string.Join(", ", generations));
```

- A) `0, 0, 0, 0`
- B) `0, 1, 2, 3`
- C) `0, 1, 2, 2`
- D) `2, 2, 2, 2`

<details><summary>Ответ</summary>

**C.** Новый объект в поколении 0; каждая пережитая сборка продвигает его на одно поколение. Поколения 3 нет: `GC.MaxGeneration == 2`.
→ [Базовая теория](basics.ru.md#поколения)

</details>

## 4. 🟢 Что вернёт `GC.GetGeneration(new byte[100_000])` сразу после создания массива?

- A) `0`
- B) `1`
- C) `2`
- D) `-1`: массив ещё не размещён в куче

<details><summary>Ответ</summary>

**C.** Объекты от 85 000 байт размещаются в куче больших объектов (LOH), которая собирается вместе с поколением 2, поэтому `GetGeneration` сразу возвращает `2`. Граница считается вместе с заголовком: на 64-битном runtime `byte[84_976]` — уже большой объект.
→ [Базовая теория](basics.ru.md#поколения)

</details>

## 5. 🟢 В каком порядке появятся строки?

```csharp
{
    using var a = new Logged("a", log);
    using var b = new Logged("b", log);
    log.Add("body end");
}
log.Add("after block");
```

`Logged.Dispose` добавляет в журнал `dispose <имя>`.

- A) `dispose a, dispose b, body end, after block`
- B) `body end, dispose a, dispose b, after block`
- C) `body end, dispose b, dispose a, after block`
- D) `body end, after block`: объявления `using` освобождаются в конце метода

<details><summary>Ответ</summary>

**C.** Объявление `using` освобождает ресурс в конце охватывающего блока — здесь это фигурные скобки, а не метод. Несколько ресурсов освобождаются в обратном порядке: `b` создан позже и может зависеть от `a`.
→ [Базовая теория](basics.ru.md#idisposable-и-using)

</details>

## 6. 🟢 Какие утверждения о `Dispose` верны? (несколько ответов)

- A) `Dispose` освобождает ресурсы вроде файлов и подключений — в момент вызова
- B) `Dispose` немедленно освобождает память самого объекта
- C) `using` вызовет `Dispose`, даже если в блоке бросили исключение
- D) GC сам вызывает `Dispose` для недостижимых объектов

<details><summary>Ответ</summary>

**A, C.** `Dispose` закрывает ресурс детерминированно, а память объекта потом освобождает GC (B неверно). `using` компилируется в `try/finally`. GC вызывает не `Dispose`, а финализатор, и только если он есть (D неверно).
→ [Базовая теория](basics.ru.md#idisposable-и-using)

</details>

## 7. 🟡 У класса есть финализатор, а `Dispose` вызывает `GC.SuppressFinalize(this)`. Объект освободили через `using`, затем он стал недостижим, и прошла сборка. Что произойдёт?

- A) финализатор выполнится, но позже
- B) финализатор не выполнится, объект будет собран обычным образом
- C) финализатор выполнится дважды: из `Dispose` и из GC
- D) объект никогда не будет собран

<details><summary>Ответ</summary>

**B.** `SuppressFinalize` убирает объект из очереди финализации, поэтому он собирается как обычный объект за одну сборку. Проверено: без `Dispose` финализатор выполнился, с `Dispose` — нет.
→ [Продвинутая теория](advanced.ru.md#финализаторы)

</details>

## 8. 🟡 Найди ошибку

```csharp
public sealed class PriceView
{
    public PriceView(PriceFeed feed) // feed is a singleton
    {
        feed.PriceChanged += (_, price) => LastPrice = price;
    }

    public decimal LastPrice { get; private set; }
}
```

<details><summary>Ответ</summary>

Утечка памяти. Лямбда захватывает `this`, делегат хранится в событии синглтона, и каждый созданный `PriceView` живёт столько же, сколько `PriceFeed`, — даже после закрытия окна. Отписаться от этой лямбды нельзя: ссылка на делегат нигде не сохранена. Исправление: обработчик-метод, отписка в `Dispose` (`IDisposable`), как в примере `Ex08_EventLeaks`: без отписки подписчик пережил сборку, с отпиской — нет.
→ [Продвинутая теория](advanced.ru.md#утечки-памяти-в-управляемом-коде)

</details>

## 9. 🟡 Что означает `disposing == false` в шаблоне `Dispose(bool disposing)`?

- A) объект уже освобождён, ничего делать не нужно
- B) вызов пришёл из финализатора: освобождать можно только неуправляемые ресурсы
- C) вызов пришёл из `using`
- D) освобождение нужно отложить до следующей сборки

<details><summary>Ответ</summary>

**B.** `Dispose()` вызывает `Dispose(true)`, финализатор — `Dispose(false)`. В финализаторе другие управляемые объекты могут быть уже финализированы, поэтому трогать их нельзя. Повторный вызов (A) отсекает отдельный флаг `_disposed`.
→ [Продвинутая теория](advanced.ru.md#шаблон-disposebool-для-иерархии)

</details>

## 10. 🟡 Сколько байт выделит добавление 1000 значений `int` в `ArrayList` и в `List<int>`, если ёмкость обоих задана заранее? (64-битный runtime)

- A) 0 и 0
- B) 4 000 и 4 000
- C) 24 000 и 0
- D) 24 000 и 4 000

<details><summary>Ответ</summary>

**C.** `ArrayList` хранит `object`, поэтому каждое значение упаковывается — отдельный объект в куче по 24 байта. `List<int>` хранит значения прямо в своём массиве, а массив уже выделен с нужной ёмкостью. Измерено через `GC.GetAllocatedBytesForCurrentThread()`.
→ [Продвинутая теория](advanced.ru.md#измерение-выделений-памяти)

</details>

## 11. 🟡 Класс реализует только `IAsyncDisposable`. Что произойдёт с кодом `using (var x = new OnlyAsync()) { }`?

- A) вызовется `DisposeAsync`, но без ожидания
- B) ошибка компиляции
- C) `Dispose` не вызовется, ресурс утечёт
- D) исключение во время выполнения

<details><summary>Ответ</summary>

**B.** Ошибка CS8418: тип в операторе `using` должен реализовывать `IDisposable`; компилятор подсказывает `await using`. Обратная ситуация — `await using` для типа только с `IDisposable` — тоже ошибка (CS8417). Классу, который освобождается асинхронно, полезно реализовать оба интерфейса.
→ [Продвинутая теория](advanced.ru.md#iasyncdisposable-и-await-using)

</details>

## 12. 🟡 Класс оборачивает дескриптор файла из нативной библиотеки. Нужен ли ему финализатор?

<details><summary>Ответ</summary>

Свой — нет. Дескриптор оборачивают в наследника `SafeHandle` и переопределяют `ReleaseHandle`. У `SafeHandle` уже есть надёжный финализатор, освобождение ровно один раз (проверено: двойной `Dispose` закрыл дескриптор один раз) и защита от закрытия дескриптора посреди вызова в нативный код. Сам класс хранит `SafeHandle` и реализует простой `Dispose`, который освобождает его.
→ [Продвинутая теория](advanced.ru.md#safehandle-вместо-финализатора)

</details>

## 13. 🔴 Что выведет код в сборке Debug?

```csharp
var obj = new object();
var weak = new WeakReference(obj);
obj = null;
GC.Collect();
Console.WriteLine(weak.IsAlive);
```

- A) `False`: ссылок не осталось
- B) `True`
- C) зависит от поколения объекта
- D) `NullReferenceException`

<details><summary>Ответ</summary>

**B.** В Debug JIT продлевает жизнь значений до конца метода, а неоптимизированный код держит копию ссылки во временной ячейке, поэтому `obj = null` не делает объект недостижимым. Проверено: `True` в Debug и при первом вызове в Release, `False` — только в оптимизированном коде. Поэтому тесты поведения GC создают объект в отдельном методе с `NoInlining`.
→ [Экспертная теория](expert.ru.md#обнуление-переменной-не-освобождает-объект-в-debug)

</details>

## 14. 🔴 Что будет напечатано?

```csharp
try
{
    using var t = new Throwing();                     // Dispose throws "from Dispose"
    throw new InvalidOperationException("from body");
}
catch (Exception e)
{
    Console.WriteLine(e.Message);
}
```

- A) `from body`
- B) `from Dispose`
- C) `One or more errors occurred.` — `AggregateException` с обоими исключениями
- D) ничего: процесс аварийно завершится

<details><summary>Ответ</summary>

**B.** `using` — это `try/finally`. Исключение из `Dispose` в блоке `finally` заменяет исключение из тела, и исходная причина теряется. Поэтому `Dispose` не должен бросать исключений.
→ [Экспертная теория](expert.ru.md#исключение-в-dispose-подменяет-исходное)

</details>

## 15. 🔴 Приложение запустили с `DOTNET_GCHeapHardLimit=10000000`. Каким будет лимит управляемой кучи?

- A) 10 000 000 байт (около 10 МБ)
- B) 268 435 456 байт (256 МиБ)
- C) 10 000 000 КБ
- D) настройка будет проигнорирована: лимит задаётся только в `runtimeconfig.json`

<details><summary>Ответ</summary>

**B.** Числа в переменных окружения GC читаются как шестнадцатеричные: `0x10000000` = 268 435 456. Проверено через `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes`. В `runtimeconfig.json` (`System.GC.HeapHardLimit`) числа десятичные.
→ [Экспертная теория](expert.ru.md#шестнадцатеричные-числа-в-переменных-окружения)

</details>
