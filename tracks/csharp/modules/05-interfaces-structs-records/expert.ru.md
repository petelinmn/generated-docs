# Интерфейсы, структуры, записи: экспертная теория

🌐 **Русский** · [English](expert.en.md)

**Уровни:** [обзор](overview.ru.md) · [1. Базовая](basics.ru.md) · [2. Продвинутая](advanced.ru.md) · **3. Экспертная**

## Под капотом

### Что компилятор генерирует для записи

Для `record Person(string Name, int Age)` компилятор добавляет в класс (проверено через рефлексию):

| Член | Назначение |
|---|---|
| `Name`, `Age` | свойства `init` (get/set-методы с модификатором `IsExternalInit`) |
| конструктор с параметрами | позиционный |
| защищённый конструктор копирования | для `with` |
| `<Clone>$()` | метод с «невозможным» в C# именем: создаёт копию, после неё применяется инициализатор `with` |
| `Equals(Person)` и `Equals(object)` | равенство по значению; запись реализует `IEquatable<Person>` |
| `GetHashCode()` | комбинирует хеши свойств |
| `==` и `!=` | операторы на основе `Equals` |
| `ToString()` и `PrintMembers` | `Person { Name = Ann, Age = 30 }` |
| `Deconstruct(out string, out int)` | для позиционной деконструкции |
| `EqualityContract` | защищённое виртуальное свойство типа `Type` |

`EqualityContract` возвращает точный тип записи (для `Person` — `Person`). Метод `Equals` сначала сравнивает `EqualityContract` обоих объектов, поэтому запись и её наследник не равны, даже если общие свойства совпали, и результат симметричен. У `record struct` вместо этого — наследование от `System.ValueType` и реализация `IEquatable<T>`: типа-контракта нет, наследовать структуры нельзя.

Позиционный параметр записи создаёт свойство; если объявить свойство с тем же именем вручную, компилятор использует ваше.

### Структуры: равенство и хеш

Структура наследует от `System.ValueType`, а реализации `Equals` и `GetHashCode` по умолчанию берутся из него (проверено: `Pt.Equals` объявлен в `System.ValueType`). Для двух структур с одинаковыми полями `Equals` вернул `True`, а хеши совпали. Реализация из `ValueType` универсальна, а значит не рассчитана на конкретный тип, поэтому для структур, которые попадают в словари и множества, **реализуйте `IEquatable<T>`** сами или используйте `record struct`, у которого он создаётся автоматически.

### Упаковка и constrained-вызовы

Вызов метода интерфейса через переменную интерфейсного типа заставляет упаковать структуру. Проверено измерением выделений: передача структуры в параметр `IInc` — **24 байта** на вызов (то же, что упаковка `int`), а передача в обобщённый метод с ограничением `where T : IInc` — **0 байт**. Для параметра типа с ограничением JIT генерирует отдельный код для каждого значимого типа и вызывает метод напрямую, без упаковки. Поэтому в «горячем» коде значимые типы передают через обобщённые методы с ограничениями, а не через интерфейсные параметры.

### Реализации интерфейса по умолчанию

Метод с телом в интерфейсе — не член класса: класс получает его только как «виртуальный» член интерфейса. Это видно по рефлексии: у `Sq` нет метода `Describe` (проверено). Если класс реализует метод сам, он используется вместо реализации по умолчанию; если два интерфейса дают одинаковые реализации по умолчанию — класс обязан реализовать метод сам (проблема ромба решается явно).

### Раскладка и размер

Структуры по умолчанию имеют последовательную раскладку (`LayoutKind.Sequential`: проверено `IsLayoutSequential == True`), поля идут в порядке объявления с выравниванием; для классов раскладку выбирает runtime (`IsAutoLayout == True`). Поэтому структура `byte, int, byte` занимает 12 байт, а `int, byte, byte` — 8 (проверено). Пустая структура — 1 байт.

| Возможность | Статус |
|---|---|
| наследование от класса/структуры | нет; можно реализовать интерфейсы |
| конструктор без параметров | C# 10+ |
| инициализаторы полей | C# 10+ (при наличии явного конструктора) |

## Подвохи

Каждый подвох проверен запуском.

### Структуру в списке нельзя изменить на месте

`list[0].X = 5;` — ошибка CS1612. Копию изменить можно, но элемент остаётся прежним: `var copy = list[0]; copy.X = 5;` → `list[0].X == 1`. Для массива `arr[0].X = 7` работает.

### Вызов метода структуры через readonly-поле

`h.Inner.Inc(); h.Inner.Inc();` для поля `readonly Inner` оставил `N == 0`: каждый вызов выполнялся над защитной копией.

### Равенство записей с коллекциями

Две записи с одинаковыми по содержимому списками **не равны**: `List<T>` сравнивается по ссылке. `with` не копирует список — изменение копии видно в оригинале (`x,y`).

### Изменяемый ключ в HashSet

После `k.Id = 2` элемент остался в множестве (`Count == 1`), но `Contains(k)` вернуло `False`.

### Equals без GetHashCode

`Contains(new NoHash(1))` → `False` для типа, у которого переопределён только `Equals`. Компилятор предупреждает: CS0659.

### Запись и наследник не равны

`new Student("Ann", 30, "MIT") == new Person("Ann", 30)` → `False`, `person.Equals(student)` → `False`. Равенство требует одинакового `EqualityContract`.

### NaN

`double.NaN == double.NaN` → `False`, а `double.NaN.Equals(double.NaN)` → `True`: оператор следует IEEE 754, а `Equals` обязан быть рефлексивным (чтобы `NaN` можно было найти в словаре). Для записей и структур с полем `double` это даёт то же расхождение.

### Метод по умолчанию не виден у класса

`new Sq().Describe()` — ошибка CS1061: метод доступен только через `IShape`.

### Присваивание в запись и запечатанный класс

`p.Name = "b"` для позиционной записи — ошибка CS8852 (только `init`); наследование от `sealed`-класса — CS0509.

### Строки и ссылки

`"a" + "b" == string.Concat("a", "b")` → `True` (сравнение по содержимому), а `ReferenceEquals(new string('a', 2), new string('a', 2))` → `False`: две разные строки в памяти.

## Компромиссы и альтернативы

| Задача | Вариант | Цена |
|---|---|---|
| Данные с равенством | `record` | не подходит для объектов с идентичностью (сущности БД) |
| | класс + ручной `Equals` | много шаблонного кода, легко ошибиться |
| Маленькое значение | `readonly record struct` | копируется целиком; большой размер вредит |
| | класс | выделение в куче, нагрузка на GC |
| Контракт | интерфейс | реализация — на каждый класс |
| | абстрактный класс | один базовый класс |
| Общая реализация в контракте | метод по умолчанию | виден только через интерфейс |
| Копирование с изменением | `with` | поверхностное |

Записи удобны для сообщений, DTO, ключей, значений предметной области. Сущности с идентичностью (заказ с `Id`, который меняется во времени) лучше моделировать классами: равенство по значению им вредит.

## Вопросы с собеседований

**1. Чем интерфейс отличается от абстрактного класса? Что выбрать?**

<details><summary>Ответ</summary>

Интерфейс — контракт без состояния и конструкторов (с C# 8 может содержать реализации по умолчанию и статические члены); класс реализует много интерфейсов. Абстрактный класс — основа с полями, конструкторами и реализованными членами, но наследование только одно. Выбор: контракт и сменные реализации — интерфейс; общая реализация и состояние — абстрактный класс.

</details>

**2. Что такое явная реализация интерфейса и зачем она нужна?**

<details><summary>Ответ</summary>

Член реализуется как `string IA.Run() => …` и виден только через приведение к интерфейсу. Нужна, чтобы разрешить конфликт одинаковых сигнатур (`IA.Run` и `IB.Run` дали `A` и `B`, а метод класса — `class`) или чтобы скрыть член от публичного API класса.

</details>

**3. Чем структура отличается от класса?**

<details><summary>Ответ</summary>

Значимый тип: присваивание копирует данные, нет собственной идентичности и наследования (только интерфейсы), всегда есть значение по умолчанию, хранится в месте объявления переменной (стек, внутри объекта или массива). Класс — ссылочный: объект в куче, ссылки, наследование, `null`.

</details>

**4. Когда структура лучше класса?**

<details><summary>Ответ</summary>

Для маленьких (по рекомендации до ~16 байт) неизменяемых значений, которые создаются в больших количествах и логически представляют одно значение. Для больших, изменяемых объектов и объектов с идентичностью — класс: копирование структуры дорого, а изменяемые структуры порождают ошибки с копиями.

</details>

**5. Почему `list[0].X = 5` не компилируется для структуры?**

<details><summary>Ответ</summary>

Индексатор `List<T>` возвращает **копию** структуры, и изменение копии было бы бессмысленным; компилятор запрещает его (CS1612). Решение: взять копию, изменить, записать обратно (`list[0] = copy`) или сделать структуру неизменяемой. Для массива это работает: элемент массива — переменная, а не копия.

</details>

**6. Что такое защитная копия?**

<details><summary>Ответ</summary>

Копия структуры, которую компилятор создаёт, чтобы вызвать её метод через `readonly`-поле или параметр `in`: иначе метод мог бы изменить «неизменяемое» значение. Из-за неё изменяющий метод ничего не меняет (проверено: `N == 0`) и добавляются лишние копирования. `readonly struct` защитных копий не требует.

</details>

**7. Что такое `record` и чем он отличается от обычного класса?**

<details><summary>Ответ</summary>

Синтаксис для типов-данных: компилятор генерирует равенство по значению (`Equals`, `GetHashCode`, `==`, `!=`), `ToString`, деконструкцию, конструктор копирования и метод для `with`. По умолчанию `record` — класс (ссылочный тип), свойства позиционных параметров — `init`. Для значимого типа есть `record struct`.

</details>

**8. Что делает выражение `with`? Глубокая ли это копия?**

<details><summary>Ответ</summary>

Создаёт копию записи (через конструктор копирования / `<Clone>$`) и применяет инициализатор. Копия поверхностная: вложенные ссылочные объекты общие — добавление в список копии изменило список оригинала (проверено).

</details>

**9. Равны ли две записи с одинаковыми значениями? А с одинаковым содержимым списков?**

<details><summary>Ответ</summary>

Записи с равными простыми значениями равны (`==`, `Equals`, одинаковые хеши). Если свойство — `List<T>`, список сравнивается по ссылке, поэтому записи с разными списками, даже одинаковыми по содержимому, не равны (проверено).

</details>

**10. Равны ли запись и экземпляр её наследника с одинаковыми общими свойствами?**

<details><summary>Ответ</summary>

Нет: `Equals` сравнивает `EqualityContract` (точный тип), поэтому `student == person` и `person.Equals(student)` дали `False` — результат симметричен.

</details>

**11. Какие правила контракта `Equals`/`GetHashCode`?**

<details><summary>Ответ</summary>

Равные объекты обязаны иметь равные хеш-коды; хеш-код не меняется, пока объект в коллекции; `Equals` рефлексивен, симметричен, транзитивен; `x.Equals(null)` — `false`. Переопределение одного без другого — предупреждение CS0659, а объекты теряются в `HashSet`/`Dictionary` (проверено).

</details>

**12. Зачем реализовывать `IEquatable<T>`?**

<details><summary>Ответ</summary>

Типизированный `Equals(T)` не требует приведения и упаковки (для структур), и именно его используют `Dictionary<TKey,…>`, `HashSet<T>` и `List<T>.Contains` (проверено: `IEquatable` вызван 2 раза, `object.Equals` — 0).

</details>

**13. Подвох: что произойдёт при изменении поля, участвующего в `GetHashCode`, у объекта в `HashSet`?**

<details><summary>Ответ</summary>

Элемент окажется «потерянным»: он остаётся в множестве (`Count == 1`), но `Contains` его не находит, потому что ищет в корзине для нового хеша. Ключи должны быть неизменяемыми.

</details>

**14. Как структура, реализующая интерфейс, попадает в упаковку? Как этого избежать?**

<details><summary>Ответ</summary>

При присваивании переменной интерфейсного типа или передаче в параметр интерфейсного типа создаётся упакованная копия (проверено: 24 байта на вызов). Избежать: обобщённый метод с ограничением `where T : IFoo` — JIT вызывает метод напрямую для конкретной структуры (0 байт).

</details>

**15. Что такое реализация интерфейса по умолчанию и каковы её ограничения?**

<details><summary>Ответ</summary>

Метод с телом прямо в интерфейсе (C# 8): позволяет добавлять члены в опубликованные интерфейсы, не ломая реализации. Ограничения: доступен только через интерфейсную переменную (`new Sq().Describe()` не компилируется); при конфликте двух реализаций класс должен реализовать метод сам; состояния (полей экземпляра) в интерфейсе нет.

</details>

**16. Что такое `static abstract` члены интерфейса?**

<details><summary>Ответ</summary>

С C# 11 интерфейс может потребовать статический член (оператор, фабрику): `static abstract T Add(T a, T b)`. Реализующий тип предоставляет его, а обобщённый код вызывает через параметр типа (`T.Add(a, b)`). На этом построена обобщённая математика (`INumber<T>`).

</details>

**17. Подвох: чем `double.NaN == double.NaN` отличается от `double.NaN.Equals(double.NaN)`?**

<details><summary>Ответ</summary>

`==` следует IEEE 754 и даёт `False`; `Equals` даёт `True`, потому что контракт требует рефлексивности (иначе `NaN` нельзя найти в словаре или множестве).

</details>

**18. Какой `==` у `string`? Почему `ReferenceEquals` для двух одинаковых строк может быть `false`?**

<details><summary>Ответ</summary>

Для `string` оператор `==` перегружен и сравнивает содержимое. `ReferenceEquals` сравнивает ссылки: две строки, созданные во время выполнения (`new string('a', 2)`), — разные объекты (проверено: `False`), хотя `==` вернёт `True`.

</details>

## Шпаргалка

| Нужно | Решение |
|---|---|
| Контракт | `interface` |
| Развить интерфейс, не ломая реализации | реализация по умолчанию |
| Два интерфейса с одним именем метода | явная реализация |
| Обобщённая математика | `static abstract` |
| Данные с равенством и `with` | `record` |
| Маленькое неизменяемое значение | `readonly record struct` |
| Структура в «горячем» коде | обобщённый метод с `where T : IFoo`, `IEquatable<T>` |

| Класс с равенством по значению | `IEquatable<T>` + `Equals` + `GetHashCode` |
